# Слой модов — как моды работают в коопе без переписывания (v1, 2026-10-22)

Часть ТЗ (`TZ.md`, принципы P2–P4). Описывает, как движок делает одиночный мод сетевым, не трогая файлы мода.
Синхронизация в целом — `SYNC_SPEC.md`, здесь — только то, что касается модов и стоковой Lua-логики.

## 1. Задача

Мод состоит из двух частей:
- **данные** — конфиги, модели, текстуры, звуки. Движок их просто читает;
- **скрипты** — вызывают функции движка (`alife_create`, `transfer_item`, `give_info_portion` …) и реагируют на
  колбэки (`actor_on_update`, `npc_on_death_callback`, `save_state` …).

Моды писали под одиночную игру: одна машина, один игрок (`db.actor`), состояние в Lua-таблицах. В коопе это
ломается тремя способами:
1. Код мира исполняется на двух машинах → два отряда, две награды, разные случайные числа.
2. Клиент меняет мир у себя → его изменение никто не видит или оно спорит с хостом.
3. Состояние мода в Lua видно только машине, где код исполнился (пример ниже, §2.4).

**Решение — не переписывать моды, а менять реакцию движка на вызовы и колбэки** (P4): каждый вызов
исполняется на правильной машине, а результат расходится штатной синхронизацией движка.

## 2. Четыре механизма

### 2.1 Данные — даром
Одинаковый набор модов у всех: при входе сверяется отпечаток модлиста (есть). Новые предметы, оружие, броня,
модели и звуки работают сразу. Объекты, созданные через классы движка, синхронизирует движок: создание,
удаление, перемещение, инвентарь, физика (есть).

### 2.2 Маршрутизатор колбэков (C++)
Решает, на какой машине вызывается каждый обработчик колбэка.

| Домен | Где исполняется | Примеры |
|---|---|---|
| `host` | только у хоста | мировые события, спавн, сюжет, выброс, смерть NPC, таймеры мира |
| `owner` | у владельца объекта: игрок — для своего персонажа и своих вещей | `actor_on_item_use` своего предмета, `actor_on_feeling_anomaly`, перки, вес, здоровье |
| `view` | у всех | HUD, звуки, частицы, интерфейс |
| `none` | нигде в коопе | механики, заменённые движком (`docs/MOD_REPLACEMENTS.md`) |

- **Как сейчас** (Ф2 задача 10). Диспетчер колбэков Anomaly — Lua (`_g.script`: `RegisterScriptCallback` →
  `axr_main.callback_set`, `SendScriptCallback` → `axr_main.make_callback`).
  - Решает движок: `coop_router.cpp` над таблицей `xrCoop/coop_routes.h`, переопределения — `configs/coop_route*.ltx`
    и `coop_compat_*.ltx`. Домен берётся **по колбэку**, правило скрипта его уточняет. Незнакомый скрипт идёт по
    колбэку: `actor_on_item_use` у клиента исполняется, `npc_on_death_callback` — нет (R5 I4).
  - Скрипт определяется по файлу, где лежит функция: `.script` — по имени, `.lua` — по пути под `scripts` через точки
    (`illish.patches.xr_combat_ignore`). Патч мода не получает правил стокового скрипта с тем же именем.
  - Исключение до маршрутизатора вызовов (§2.3, задача 12), решения F2-28 и F2-29:
    - скрипт, который зовёт функции мира и не имеет своего правила, у клиента не выполняется, как до задачи 10;
    - списки генерирует `tools/gen_route_world.lua` в `coop_route_stock.ltx` (сток Anomaly) и
      `coop_route_gamma.ltx` (рыхлые скрипты GAMMA); пересобирать после обновления GAMMA или Anomaly;
    - таймеры (`AddUniqueCall`, `CreateTimeEvent`) скрипта без правила — `host`;
    - точечная правка — в своём `coop_compat_<мод>.ltx`: эти файлы читаются последними и перекрывают сгенерированные.
  - В Lua осталась прокладка `scripts/coop_route.script` (у хоста и у клиента). Она один раз, при регистрации,
    оборачивает обработчик доменом из `coop.route.of` и на каждый вызов спрашивает `coop.route.runs`. Оборачивает
    `callback_set/unset`, `AddUniqueCall/RemoveUniqueCall` и `CreateTimeEvent`; `make_callback` не трогает.
  - Вне сессии исполняется всё. `none` пропускается и у хоста. У клиента обработчик идёт под `pcall`: ошибка
    считается, сессия живёт.
  - Счётчики в `coop_status`: строки `[coop] routes`.
  - Ещё не в движке: колбэки, которые движок шлёт сам (биндеры), — задача 11.
- **Как надо.**
  - Таблица маршрутов в C++: ключ — пара (имя колбэка, скрипт обработчика), значения по умолчанию заданы для
    каждого стокового колбэка. Домен определяется **по колбэку**, а не по файлу: `actor_on_item_use` своего
    предмета — `owner` у кого угодно.
  - Переопределения — в ltx (`coop_route_*.ltx`, DLTX).
  - В Lua остаётся одна прокладка: `axr_main.callback_set/unset/make_callback` зовут движок. Это неизбежно,
    потому что диспетчер стока написан на Lua.
  - Колбэки, которые движок шлёт сам (вызовы биндеров объектов, `set_callback` игровых объектов), движок
    маршрутизирует до входа в Lua. Сюда переезжают 28 клиентских патчей биндеров W10
    (`coop_client_binders.script`).
- Счётчики в `coop_status`: вызвано, пропущено и ошибки по каждому домену.

### 2.3 Маршрутизатор вызовов (C++)
Решает, что делает функция движка, вызванная из Lua на этой машине.

| Класс функции | Примеры | У хоста | У клиента |
|---|---|---|---|
| `world` — меняет мир | `alife():create/release`, `transfer_item`, `give_info_portion` (не UI), задания, отношения, деньги NPC, `kill`, удар по чужому, погода, время | исполняет | становится запросом хосту → хост проверяет (P8) и исполняет → результат приходит событием |
| `owner` — своё | свой актор: здоровье, потребности, бустеры, активный слот; свой инвентарь | для своего | для своего |
| `view` — картинка и звук | HUD, UI, звук у себя, частицы, камера, эффекторы | локально | локально |
| `read` — чтение | позиции, `alife():object`, время, инфопорции | локально | локально (зеркало мира хоста) |

- Класс задаётся таблицей в движке по каждому экспорту luabind:
  - `alife_simulator_script.cpp`;
  - `script_game_object*.cpp`;
  - `level_script.cpp` и др.
  Переопределения — в ltx.
- Проверки аргументов в одном месте: NaN/inf, диапазоны, существование id, дистанция до игрока, частота по имени
  функции (R3 В5–В8, R6 I-2).
- **Функции с немедленным результатом.** Пример: `alife_create` возвращает объект с id, и мод сразу им
  пользуется. Предложение:
  - хост выдаёт каждому клиенту резерв id;
  - клиент создаёт объект сразу с id из резерва, Lua получает его синхронно, как в одиночке;
  - запрос уходит хосту: тот подтверждает тот же id или откатывает (удаление у клиента, запись в журнал).
  - Требует разведки: какие поля CSE заполняет клиент и как откат действует на мод.
- **Сейчас.** Часть пути уже есть: маршрутизатор `CLevel::Send`, ReqSpawn, ReqHit, торговля, контейнеры. Нет единой
  таблицы и покрытия всех экспортов.

### 2.4 Зеркало состояния модов (C++)
Моды хранят состояние в `m_data` через колбэки `save_state` / `load_state`. Пример — Hideout Furniture:
`m_data.player_created_stashes`, `m_data.workshop_stashes`, `spawned_objects` (`hf_map_objects.script`). Палатку
клиент увидит (§2.1), но для его копии мода она «чужая»: таблица пуста.

- При входе клиент уже получает `m_data` хоста целиком: это `.scoc` в сейве мира.
- **Нужно живое зеркало:**
  - хост после колбэков домена `host` (не чаще 1 раза в 2 с) снимает `m_data`, считает разницу по ключам верхнего
    уровня и рассылает её;
  - клиент применяет изменения до вызова колбэков мода;
  - свои изменения `m_data` клиент не рассылает: только через запрос (§2.3);
  - лимиты размера на ключ и на пакет;
  - локальные ключи (интерфейс, настройки игрока) перечисляются в ltx и не зеркалятся.
- То же для хранилища объектов (`se_save_var` / pstor): данные едут вместе с объектом (частично есть как `se_store`).
- Что не видно: состояние в локальных переменных скрипта (upvalue), которое не попадает в `m_data`. Для таких модов —
  декларация (§2.5) или патч.

### 2.5 Декларации и патчи (крайний случай)
Если 2.1–2.4 не хватает, мод получает, по возрастанию цены:
1. **Декларацию в ltx** (5–20 строк): домен колбэков скрипта, класс функции, локальные ключи `m_data`.
   Файл `configs/coop_compat_<мод>.ltx` в нашем моде, действует только если мод установлен.
2. **Тонкий патч на Lua** через `coop.sync` (`SYNC_SPEC.md` §6): общие переменные, действия через хост, эффекты.
   Файл `scripts/coop_compat_<мод>.script`. Своих сетевых протоколов патч не строит.
3. **Замену движком** — механика становится частью игры, мод выключается или урезается. Запись в
   `docs/MOD_REPLACEMENTS.md`.
4. **Отметку «несовместим»** с причиной.

## 3. Уровни совместимости мода

| Уровень | Значит | Чем достигается |
|---|---|---|
| A | работает сам | §2.1–2.4 |
| B | работает с декларацией | §2.5.1 |
| C | работает с тонким патчем | §2.5.2 |
| D | заменён движком | §2.5.3, `docs/MOD_REPLACEMENTS.md` |
| X | несовместим | причина в каталоге |

Каталог по модам GAMMA — `docs/GAMMA_COMPAT.md`, создаётся в Ф4. Цель: большинство модов — A и B.

## 4. Что переезжает из Lua в движок (Ф2)

Списки из ревью: R1 «Перенос в движок», R4 7, R5 I3, R6 (a) и (b).
- деньги;
- маршрутизация заданий и наград (`coop_tq`, `coop_tl`, `quests.*`);
- пропуск времени, телепорты и маршруты (`economy.tp/route`);
- выброс и пси-шторм (`coop_env`);
- настройки хоста (`coop_set`);
- данные предметов и игроков (`se`, `imd`, `pmd`, `wmd`, `coop_mods_pdata`);
- секции логики рестрикторов;
- лут мутантов, «тайник найден», профиль торговца (`coop_core_world`);
- `core.status`;
- огонь, звуки, мины и маскировка NPC;
- RF, КПК, рейтинг, энциклопедия.

Протоколы `coop_mods_*` переходят на §2.2–2.5. Lua-фильтр доменов уходит в движок (§2.2).

## 5. Проверка

- Стаб-тесты маршрутов на LuaJIT движка (`tests/lua/`): таблица по умолчанию, переопределения ltx, незнакомый скрипт.
- `coop_status`: счётчики маршрутов, отказов и зеркала (ключи, байты).
- Сценарии на модах GAMMA: Hideout Furniture (палатка, тайник, верстак), мины, компаньоны, бесшумные убийства,
  Mags Redux, BHS, ставные костры — у хоста и у клиента.

## 6. Открытые вопросы

- Резерв id для `alife_create` у клиента (§2.3): поля CSE, откат, влияние на моды.
- Колбэки «на игрока» у хоста: моды, которые на хосте должны работать для прокси игрока (подмена `db.actor`), —
  разведка по модам GAMMA в Ф4.
- Частота и стоимость снятия `m_data` на больших сборках (GAMMA): замер в Ф2.
