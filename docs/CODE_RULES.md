# Правила написания кода RayLink Coop

Свод обязателен для всех, кто пишет код в этом репозитории и в движке (`engine/`): для ведущей, для агентов Opus и Sol.
Читать его нужно до того, как начинаешь писать код. Выжимка лежит в `CLAUDE.md` и `AGENTS.md`, но решает полный текст этого
файла. Лаунчер (`raylink-launcher`, Rust и TypeScript) живёт в своём репозитории, этот свод его не связывает (§13).

Слова владельца (Р110, 2026-11-26): «обязательно не забудь промт который исключает абсолютно каждую ошибку при написании кода,
все то что мы нашли не должно больше повторяться, правила написания кода приветствуются».

## Как пользоваться

- **Откуда правила.** Правил «на всякий случай» здесь нет: каждое правило закрывает ошибку, которую мы уже сделали.
  Источники:
  - 385 подтверждённых находок большого ревью Р107;
  - разборы Р106 (движок знает моды; адаптеры с развилками режима);
  - история багов ТЗ §6 (Р30–Р104);
  - решения владельца (ТЗ §2–§5, §6.33–§6.35).

  Таблицу «находка → правило» ведущая собрала при своде. Каждая находка ведёт либо на правило, которое её запрещает, либо на
  §13 «Что правилом не закрыто».
- **Как применять.** До кода прочитай разделы своей области. Перед сдачей работы (исполнитель) и перед коммитом (ведущая)
  пройди чек-лист §11. В ревью и отчётах ссылайся на номер правила (`LAYER-1`, `BUG-8`).
- **Строение правила.** Правило, почему оно есть, «плохо» (наш собственный код) и «хорошо» (тоже наш код или точный образец).
  В конце — чем нарушение ловится:
  - `lint:Ln` — проверка `tools/check_layers.py`, она уже есть;
  - `будет: Ln` и `будет: Sn` — проверки, которых ещё нет: новые правила `check_layers.py` и `tools/check_static.py`. Каждая
    стоит в таблице §14: что она ловит (одной строкой) и какой пакет её делает;
  - `test:` — тест;
  - `ревью` — проверяет человек или агент по чек-листу.
- **«Хорошо» показывает только названный приём.** Другие нарушения в том же файле (пустышка `C()`, коды работ в шапке, свой
  глагол в соседней строке) — долг своих правил. Их не копируют.
- **Пометка «будет».** Помощника, файла, хука или проверки ещё нет, их создаёт названный пакет. Если без этого механизма
  задачу не сделать, не пиши «как соседний код»: остановись до кода и доложи ведущей (OWN-18).
- **Номера.**
  - `пакет Pn` (P0–P35) — пакет плана уборки Р107. В пометке «будет: пакет Pn» и в скобках вида «(P24)» голое `Pn` — всегда
    пакет;
  - `принцип Pn` (P1–P15) — принцип ТЗ §5; он всегда пишется со словом «принцип»;
  - `Fn` (F1–F11) — пакет исправления ошибки из ревью Р107;
  - `шаг Sn` — шаг плана разделения режимов `docs/plans/2026-11-18-two-modes.md`; `шаг N Р106` — общий механизм движка из
    разбора Р106 (ТЗ §6.33);
  - `Ln` и `Sn` без слова «шаг» — проверки (§14);
  - `Рnn` — строка таблицы §2 ТЗ со словами владельца.
- **Пути.** Пути C++ даны от `engine/src/`, скрипты Lua — от `gamedata/scripts/`, остальное — от корня репозитория.
  Номера строк сверены 2026-11-26 с рабочим деревом, где уже лежат правки F1, F3–F7, F9 и F10. «Плохо», которое эти правки
  убрали, указано по коммиту до правки: мод `82206f06`, движок `4dd9c6aeb` (для F5 — `bd4d1cf77`). Когда код сдвинется, ищи
  по имени функции.
- **Потолки.** Сегодняшние нарушения перечислены в списках исключений (`tools/layers_allow.txt`). Их число только уменьшается.
  Новое нарушение — отказ, даже если «рядом уже так». Новую строку долга может разрешить только ведущая (OWN-18).
- **Если правило мешает.** Не обходи его, скажи ведущей. Правило меняется только решением владельца: сначала строка в ТЗ,
  потом правка этого файла.

3. MOD — моды и сборки.

## 1. OWN — порядок работы и общие правила кода

### OWN-1. Слово владельца — в ТЗ, потом исполнение
**Правило.** Каждое решение, пожелание или правку владельца в тот же ход:
1. записать в `TZ.md`: строка в таблице §2 с его словами, текст — в нужном разделе §6;
2. исполнить без отдельной команды.

Вывод ведущая заносит в vault. ТЗ исполняется целиком. «Делать ли?» не спрашивают; спрашивают, только когда работа
заблокирована: нет доступа, нужны боевые деньги, действие необратимо. Решения ТЗ §2–§5 — это инварианты продукта (их
примеры ниже). Код, который им противоречит, — ошибка.
Свой черновик ведущая помечает словом «предложение». По открытым вопросам §7 ничего не меняют до ответа владельца.

Примеры инвариантов: задания общие (принцип P6), игровых сейвов у игроков нет (принцип P7), в Сервере карты независимы
(принцип P11).

**Почему.** Решение, которое осталось только в чате, теряется, а ТЗ — единственный источник требований для всех агентов.

**Хорошо:** Р111 — строка в §2 со словами владельца и §6.35 с работой, оба в одном коммите `81659e05`.

**Проверка:** ревью.

### OWN-2. Каждый режим отдельно
**Правило.** Фича, правка поведения и баг проходят по каждому режиму отдельно:
1. До кода записать для Коопа и для Сервера: кто решает, какие данные у него есть (карта, ИИ-сетка, отношения, инвентарь), кто
   и чем сообщает ему недостающее.
2. Режимная часть — отдельная функция или файл своего слоя. Общая чистая логика — в `xrCoop/*_rules.h`.
3. У каждого режима свой тест или свой сценарий стенда. Один сценарий на оба режима не засчитывается. Тест нового поведения
   пишется до кода по записи из п.1 и без кода падает (для бага — OWN-6). Правка только слоя Сервер: тест Сервера, набор
   кооп-тестов без изменений (LAYER-3).
4. В отчёте — строка на режим: «сделано и проверено / сделано, не проверено / не сделано / не нужно». «Не нужно» пишется с
   причиной: «Кооп: не нужно — у Коопа нет серверов карт».
5. В `docs/TESTERS.md` — пункт на каждый режим.

**Почему.** То, что работает в Коопе, ничего не говорит о Сервере: у сервера мира нет карты игрока.

**Плохо:** `coop_mods_view_fixes.script:32` — `if not coop_mode.decides_world() or not coop_mode.leads_here() then return end`.
Правка продумана только для кооп-хоста. В Сервере ни у одного процесса нет обоих ответов сразу, поэтому подсказку
`zzz_tasks_guide` не снимает никто (вывод по коду, в игре не проверено).

**Хорошо:** ТЗ §6.28 (Р99): причина и правка отдельно для Коопа и для Сервера, тесты
`tests/lua/test_hostplay_mods_wpo_stamps.lua` и `tests/lua/test_srv_mods_wpo_stamps.lua`, пункты тестеров на каждый режим.

**Проверка:** ревью; `tools/check_gates.py` (метки `hostplay.ok` и `srv.ok`).

### OWN-3. Список для тестеров
**Правило.** Если ты сделал или поменял поведение, которое видит игрок, и не видел его в живой игре, в тот же ход добавь
пункт в `docs/TESTERS.md`. Формат пункта: «что сделать → что должно получиться», с какой сборки, в каком режиме. Номер
`К-…` — для Коопа, `С-…` — для Сервера, на каждый режим отдельный пункт, номер — следующий свободный в файле на момент
коммита. Если ожидаемое неизвестно, пункт так и называется: «сбор данных». Когда владелец или тестеры подтвердили, пункт
уходит в «Проверено» с датой и сборкой. Не подтвердилось — заводится баг, пункт остаётся. Пункты пишутся только для
включённых модов (MOD-7). Шапка файла называет текущие сборки каналов.

**Почему.** Список уходит тестерам: непроверенное поведение без пункта никто не проверит, а одинаковые номера смешивают
результаты.

**Плохо:** пункты арены получили номера пунктов про артефакты (ТЗ §6.19); К-350 сначала записали как «ожидается 0», хотя
Т-поза была и в Коопе (ТЗ §6.30); шапка `docs/TESTERS.md` называет Dev 63, а уже выпущены `dev-64` и `dev-65`.

**Хорошо:** К-330 (Р102): «Хост и клиент: упасть при смерти → у тебя в ленте …», с пометкой, с какой сборки.

**Проверка:** ревью.

### OWN-4. «Работает» — только после проверки
**Правило.** Слова «работает», «совпадает», «исправлено», «быстрее» можно писать только после теста, команды или замера в
этой же работе. Иначе пиши «не проверено» и уточняй: «по коду» или «в игре не проверено». Факт о живой системе пишется с
датой и временем проверки. Про порт «верно» говорят только после сравнения с числами исходника или нативного оракула
(OWN-7). Порядок отчёта:
1. строка на каждый режим;
2. файлы;
3. команды и их итоги;
4. что не поддержано или не проверено.

**Почему.** Утверждение по памяти или по чтению кода выдаёт гипотезу за факт, а владелец и следующие агенты действуют по
отчёту.

**Хорошо:** ТЗ §6.30: «Итог разбора (2026-11-26, по коду и данным G.A.M.M.A., в игре не проверено)».

**Проверка:** ревью.

### OWN-5. Сначала причина; правка — в общем месте
**Правило.** До правки нужна причина с доказательством для каждого режима: код, журналы, отчёты RayLink-Reports, проба. Порядок
разбора:
1. Проверить само наблюдение: что на самом деле показывает игра, что значит число.
2. Проверить, не дефект ли это стока или G.A.M.M.A., который есть и в одиночной игре.
3. Проверить, включён ли мод в профиле.

Чинить одним правилом в общем месте. Общее место — точка, через которую проходят все пути сломанного потока (создание и
удаление, все виды процессов, где этот поток идёт), в слое, которому поток принадлежит. Поток только Сервера чинится в
`srv/`, а не в Ядре; поток обоих режимов — в Ядре. Заплатки на одном пути, окна по времени («второй раз за N с — не
выдавать»), особые случаи и повторы «на всякий случай» запрещены. Если у движка уже есть цепочка (речь NPC, звук, анимации),
игрок идёт через неё же. Ограничение X-Ray обходят новым общим методом движка, а не костылём в Lua (CPP-19). Неизвестную
причину гипотезой не закрывают: добавляют строку диагностики и записывают, как отличить одно от другого.

**Почему.** Заплатка на одном пути оставляет баг на остальных, а правка того, чего на самом деле нет, ломает честное
поведение.

**Плохо:**
- «5 → 10» при выдаче отладкой: на награды ставили окно «3 с» и диагностику, а задвоения не было. QoL Bundle
  (`stacks_to_uses.script`) просто показывает на стопке сумму зарядов (ТЗ §6.9).
- `xrGame/coop/coop_instrument.cpp:78` — отдельный модуль под гитару и гармошку вместо общей ретрансляции звуков и анимаций
  игрока.

**Хорошо:** отказы «not the writer» (ТЗ §6.32). Все строки разобраны до правки, а правка сделана в двух общих местах:
`client_remember_held` (`xrGame/coop/srv/coop_levels_xfer.cpp`) и `unchanged_parent` (`xrCoop/srv/coop_levels_accept.h:122`).

**Проверка:** ревью. В описании правки должна быть причина с доказательством по каждому режиму и объяснение, почему это не сток
и не выключенный мод.

### OWN-6. Исправление — отдельный пакет со своим падающим тестом
**Правило.** Уборка не меняет поведение, исправление меняет; это разные пакеты.

Порядок исправления:
1. Тест, который без правки падает по нужной причине. Это проверяют откатом или подменой кода. Для каждого режима свой тест:
   - Lua — под наборами `hostplay` / `srv_world` / `srv_map` / `none` (`tests/lua/support/modes.lua`);
   - нативный — под `MODE_CASES` (`tests/support/fake_mode.h:53`);
   - сценарий — SC или SS.
2. Правка.
3. Проверка скептиком.
4. Пункт TESTERS на каждый режим (OWN-3).
5. Строка отчёта на каждый режим.

Уборку и оптимизацию доказывают неизменные тесты обоих режимов: утверждения и ожидаемые значения тестов не меняются. В
пакете уборки разрешены только две правки тестов, и обе перечисляются в описании пакета:
- путь или сигнатура среза меняются, когда функция переезжает в другой файл (OWN-14, TEST-8);
- тесты удалённого мёртвого кода или ветки выключенного мода удаляются в том же коммите (OWN-12, MOD-7).

Если пакет «уборки» меняет тайминг, порядок или общее состояние, это исправление.

Строка долга из allow-list (`tools/layers_allow.txt`) — ключ `правило|путь|код|счётчик`. Если исправление меняет такую
строку, ключ меняется, и проверка откажет. Тогда либо долг сначала гасит отдельный коммит уборки, либо ведущая заменяет ключ
в allow-list с тем же счётчиком (`--write-allow --reset-ceiling`) и пишет об этом в описании исправления.

**Почему.** Только тест, который падал без правки, доказывает, что он ловит ошибку. Смешанный пакет нельзя доказать словами
«поведение не изменилось».

**Плохо:** `tests/tools/test_gates.py:3209` `test_lua_stamp_of_this_repository_is_the_runners_when_it_is_fresh` всегда уходит в
`pytest.skip` — ошибку штампа он не поймал ни разу.

**Хорошо:** `tests/lua/test_hostplay_rider_stamp.lua` и `tests/lua/test_srv_rider_stamp.lua`. Без правки оба падают: это
проверено подменой каждого места по одному (ТЗ §6.28).

**Проверка:** ревью. В отчёте пакета F — команда и вывод прогона без правки (падение) и с правкой (зелёный) по каждому режиму.

### OWN-7. Точный перенос
**Правило.** Логику мода и стока к себе не переносим: её исполняет сам мод (MOD-1, MOD-3). Если перенос неизбежен (механизм
движка повторяет поведение C++ стока, Lua-порт функции C++, нативный тест-оракул):
- функцию исходника читают целиком вместе с вызываемыми;
- каждый вызов переносят со всеми явными аргументами (части и каналы анимации, флаги, смешивание), значение библиотеки по
  умолчанию не подставляют;
- каждый объект, который создаёт исходник, есть в порте в той же роли. Слияние или упрощение — это изменение поведения: о нём
  пишут в отчёт, а не внедряют;
- «совпадает» говорят только после сверки с числами исходника.

**Почему.** Упрощённый перенос даёт расхождения, которые видит игрок. Копия кода мода расходится с модом при его обновлении.

**Плохо:** у копии NPC флинчи попаданий каналов 2/3 игрались как цикл канала 0 (сборка 29, ТЗ §6.30);
`coop_srv_factions_gamma.script:14` — перемирие сталкеров из G.A.M.M.A. переписано своими таблицами.

**Хорошо:** вызов в порте повторяет канал, смешивание и флаги исходника; тест сравнивает числа с формулой C++ или с нативным
оракулом.

**Проверка:** ревью (чек-лист порта); тест против чисел исходника.

### OWN-8. Границы исполнителя
**Правило.** Исполнитель трогает только файлы своей задачи и не откатывает чужие правки: перед правкой смотрит `git status`,
чужие незакоммиченные файлы не трогает. Исполнитель не делает:
- запись в индекс и HEAD git;
- заметки в vault;
- вложенных агентов;
- сборку движка.

Всё это делает ведущая. Свои идеи сверх задания (оптимизация, уборка, другой подход) исполнитель пишет в отчёт, а не
внедряет.

Пути владельца — один список, у каждого свой доступ:

| Путь | Доступ |
|---|---|
| `E:\RayLinkGames\GAMMA\game`, `E:\Programs\RayLink`, `%APPDATA%\RayLink` (живая игра владельца) | никто не читает, не пишет и не запускает |
| `E:\RayLinkGames\GAMMA\mo2` | только чтение, только ведущая: `profiles\G.A.M.M.A\modlist.txt` и файлы модов. Исполнитель берёт имена модов из `tools/mod_names.txt`, скрипты — из копий для чтения |
| `E:\RayLinkGames\GAMMA\game-dev` (стенд, TOOL-2) | чтение — все; запись — только помощники стенда; запуск — только при закрытой игре владельца |
| `temp/review/corpus/merged/`, `temp/stock_scripts/scripts/` (копии для чтения) | только чтение |

`temp/` — только место вывода, рабочих и промежуточных файлов прогона: метки ворот `temp/gates`, сборка Lua-прогонщика
`temp/lua`, фикстура `work`, черновики агента. Неотслеживаемые данные из `temp/` код, тесты и инструменты не читают как вход.
Комментарии и документы продукта не называют путей `temp/` и абсолютных путей машины (TEST-4, DOC-1). Скрипты, которые
сегодня живут в `temp/` и названы в промтах (`temp/build_guarded_fast.ps1`, `temp/b58/run_units.ps1`), — долг TOOL-3, их
переносит пакет P2.

### OWN-11. Обёрток-пустышек нет
**Правило.** Нет функций, которые только возвращают свой аргумент или только передают вызов дальше. Модуль связывается один

**Плохо:**

## 2. LAYER — слои и режимы

Режимов два: **Кооп** (хост играет сам, все на одной карте) и **Сервер** (сервер мира без игрока плюс серверы карт). Слоёв
кода три: **Ядро** (общее), **Кооп** (`hostplay`) и **Сервер** (`srv`). Подробно — `docs/MODES.md`.

Три слова, которые свод различает:
- **Ядро** — слой по правилам режима: все файлы без метки слоя (`tools/layers.txt`). Сюда входят и адаптеры `coop_mods_*`:
  для LAYER-1…LAYER-3 и проверок L1–L12 адаптер — Ядро.
- **Общие файлы** (Р113) — Ядро без адаптеров плюс слои режимов. Они не называют ни мода, ни сборки (MOD-2).

### LAYER-1. Ядро не знает, в каком режиме работает

### LAYER-3. Где начинается фича и как принимают правку Ядра
**Правило.** Новая фича начинается в слое своего режима (`hostplay/`, `srv/`, `coop_hostplay_*`, `coop_srv_*`). В Ядро она
переезжает, только когда нужна обоим режимам и ведёт себя в них одинаково. Новый ответ режима добавляется в интерфейс
(`xrCoop/coop_mode.h`, `coop_mode.script`) сразу с ответами `hostplay`, `srv` и `none`.

Правкой Ядра считается и правка любого из этих файлов:
- стоковый файл движка;
- таблицы `coop_route*.ltx`, кроме замены `host` ↔ `level`;
- протокол `coop_protocol.h`;
- любой файл, у которого есть строки в `tools/layers_allow.txt`.

Как принимают правки:
- правка Ядра — с нативными и Lua-тестами под всеми наборами ответов и стендами обоих режимов на одном exe;
- правка только `srv` — тест и стенд Сервера, набор кооп-тестов не меняется, в отчёте строка «Кооп: не нужно — почему»;
- `hostplay` и `srv` в одном коммите без Ядра — коммит делится.

**Почему.** Сток, маршруты и протокол работают в обоих режимах. Правка `GetLuminocity` для серверов карт (`88a20a9b`)
поменяла Кооп без единой проверки режима.

**Хорошо:** хук в стоке — одна строка с вызовом функции Ядра: `coop::players::own_condition_held(this)` (`docs/MODES.md` §5).

**Проверка:** `tools/check_gates.py` (правка Ядра требует `hostplay.ok`, `srv.ok`, `tests.ok`; `hostplay` + `srv` без Ядра —
«раздели коммит»); `test: tests/tools/test_gates.py`, `tests/tools/test_layers.py`.

### LAYER-4. Номера мостов и серверов карт в Lua не пишутся
**Правило.** Номера мостов и серверов карт (`0x100`, `0x101..0x107`, `256`, `from < 0x100`, `peer >= 0x100`) в Lua не
пишутся ни в одном слое. Вопрос «сообщение пришло от сервера карты?» задаётся через `coop_mode.from_level(from)`. Номер карты

**Почему.** Правило движка (`xrCoop/srv/coop_mapserver_rules.h`) в копии на Lua расходится с оригиналом: `from < 0x100`
считает мостом и сам 0x100, и всё выше 0x107. В Ядре такие числа — скрытая развилка Сервера.

**Плохо:** `coop_srv_quests_far.script:911` `if not world_server() or type(from) ~= "number" or from < 0x100 then return end`.

**Хорошо:** `coop_mode.script:288-292` `from_level(from)` — ответ даёт слой режима.

**Проверка:** `будет: L13` (литералы мостов и сравнения `from`/`peer` с 256 в `coop_*.script` — потолок по файлу).

### LAYER-5. Слой Сервер берёт роль из фасада; гибрида нет
**Правило.** Слой Сервер (`coop_srv_*`) не определяет «сервер мира / сервер карты» заново в каждом файле. Роль процесса он
берёт из фасада (`coop_mode.decides_world`, `leads_here`, `is_player_mirror`) или из одного серверного помощника. Веток под
гибрид (`is_host` без dedicated) нет. Обёртки ролей, которыми пользуется только Сервер, живут в слое Сервер, а не в Ядре с
пометкой «совместимость».

**Почему.** Пять самодельных определений роли расходятся по смыслу: например, до начала сессии фасад и `api.is_host` отвечают
по-разному. Гибрид удалён решением владельца от 2026-11-18, его ветка — мёртвый код.

**Плохо:** `coop_srv_levels_brain.script:65-67` `local function world_server() return api ~= nil and api.is_host() == true end`;

**Хорошо:** `coop_mode.decides_world()` — один ответ, который слой `srv` даёт по своим правилам.

**Проверка:** `lint:L6` (надгробия гибрида); `будет: L22` (`api.is_host(` в `coop_srv_*` — потолок); ревью.

### LAYER-6. Сохранённые имена не трогаем
**Правило.** Ключи записи мира (`c|…`), ключи pstor/marshal и имена событий на проводе не переименовываются и не удаляются;
их список — `tools/persisted_keys.txt`. Если имя нужно сменить (Р4), старое живёт синонимом одну Dev-сборку. Ключи убранного

**Почему.** Пропавший ключ ломает старые миры и договор с лаунчером: например, по `c|coop_world_server` лаунчер разрешает
кнопку «Запустить сервер».

## 3. MOD — моды и сборки

Решения владельца Р106, Р111–Р113: «движок это просто по сути должен быть инструмент с АПИ для модов»; «не нужно заставлять
моддеров писать код и туда и туда, это забота движка»; «все что мы можем делать, это переписывать стоковые файлы аномали»;
«для каждой сборки будет своя обвязка».

### MOD-1. Движок не знает модов
**Правило.** В C++ движка (все слои и правленый сток, без `3rd party`) нет ничего про конкретный мод:
- имён его скриптов, функций, секций и данных;
- литералов `coop_mods_*`;
- формул, диапазонов и констант, списанных с мода;
- вызова наших адаптеров по имени.

Движок даёт только общие механизмы: объекты, владение, маршрут вызовов, данные на предмете, зеркало анимаций и звука, реестр
в Lua-модуле Ядра, секция данных ltx. Знание о моде регистрирует его адаптер. Пределы, которые зависят от размера сборки,
берутся из загруженного мира или из настроек.

**Почему.** Мод описывается один раз, в своём адаптере (Р106). Логика под мод в движке ломается с обновлением мода и не
годится другим сборкам.

**Плохо:**
- `xrGame/coop/coop_trade.cpp:305` `lua_getglobal(L, "coop_mods_trade_computer");`;
- `xrCoop/coop_zone_path_rules.h` — формула пути «Призрака» из DAO;
- `xrGame/coop/coop_instrument.cpp:78` `return kind == 1 ? "guitar_a" : "harmonica_a";`;
- `xrGame/coop/coop_requests.cpp:670` `constexpr const char* kRiderScript = "coop_mods_item_state";` — движок зовёт адаптер
  по имени (строка долга L12); заголовок `xrCoop/coop_item_rider_rules.h` описывает механизм через
  `coop_mods_item_state.carry` / `carried`.

**Хорошо:** `xrCoop/coop_routes.h` — таблица маршрутов называет только стоковые колбэки, а правила скриптов модов лежат
данными в `gamedata/configs/coop_route_mods.ltx`.

**Проверка:** `lint:L12`. Он ловит литерал `coop_mods_`, имена скриптов из `tools/mod_names.txt` и прозвища GAMMA, DAO, 3DSS,
YACS, PAW, MCM, Gadgets. Долги разбора Р106 (места R1–R4 и вызовы адаптеров G1/G2, ТЗ §6.33) записаны в
`P106_TODAY` в `tests/tools/test_layers.py`: тест не даёт списку расти. Ревью: формулы мода под нашими именами — L12 видит
только имена.

### MOD-2. Общие скрипты не называют ни мода, ни сборки
**Правило.** Lua-файлы Ядра (`coop_*.script`, кроме `coop_mods_*`) и слоя Сервер не называют мод или сборку. В них нет:
- имён скриптов, функций, секций и ключей `m_data` мода;
- обращений к адаптеру (`module_of("coop_mods_…")`);
- таблиц под конкретный мод.

Вместо этого они дают точку подключения (хук, список правил, данные в ltx), и адаптер регистрируется в ней сам. Стоковые
скрипты Anomaly (`death_manager`, `xr_eat_medkit`, `sim_squad_warfare`, `ui_enemy_health`) называть можно: это аномалевский
стык (MOD-9).

**Почему.** Общий файл должен работать на любой сборке (Р113). Ядро, которое зовёт адаптер по имени, нельзя проверить без
этого мода.

**Плохо:**
- `coop_trade_window.script:239` `local holder = module_of("coop_mods_wpo_holder")`;
- `coop_main.script:1054` `local CROW_WARNING = {` — звуки Preblowout Murder в шине событий;
- `coop_route.script:133` `local ROTATE = { xcv_phantoms = true, …`.

**Хорошо:** `coop_mods_world_views.script:342` `coop_economy_mdata.register_world_key(PARTS_KEY)` — ключ мода регистрирует сам
адаптер, общий файл имени мода не знает. Пример показывает только эту строку: соседние `:340-341` (`wrap` с решением «кто
решает») и `:343-344` (`set_limit` и `on_big`, свой глагол) — долг MOD-4, а сам `register_world_key` — долг LUA-3 (MOD-5).

**Проверка:** `будет: L15` (имя из `tools/mod_names.txt` и литерал `coop_mods_` в общих скриптах — потолок по файлу); ревью:
srv-файл, который называет мод.

### MOD-3. Один мод — один адаптер, общий для обоих режимов
**Правило.** Всё знание о моде лежит в одном файле `coop_mods_<мод>.script`, названном по моду, которому он служит. Файл один
на Кооп и Сервер. По правилам режима он Ядро (LAYER-1), по набору — часть набора сборки (MOD-9). Режим в нём спрашивается
только вопросом к фасаду: «решаю ли я здесь?» как охрана («не решаю — ничего не делаю») и «где объект?». Слой Сервер не
описывает мод второй раз. То, что нужно Серверу, адаптер объявляет через `coop_mode.share_up` / `share_down` (есть) или через
`up` / `to_level_of` / `on_report` (будут, шаг 2 Р106).

Точка крепления к моду — обёртка функции мода через `coop_mods_core.wrap`: так адаптер после обновления мода встаёт на то же
место (Р112, ТЗ §6.33). Правила обёртки:
- одна функция мода — одна обёртка из одного файла; несколько изменений одной функции — одна обёртка с явным порядком и
  тестом на этот порядок;
- результат `wrap` проверяется, не встала — громкая строка (MOD-8);
- внутри нет сетевой механики: своего сообщения, ветки «у решающего, иначе шлю», подмены личности (MOD-4);
- обёртка — точка крепления, а не место для механики. Адаптеры остаются: к моду, который нельзя править, иначе не
  подключиться. Но где общий механизм движка закрывает случай сам (маршрут по колбэку, зеркало `m_data`), обёртка
  убирается. Число обёрток в адаптерах только убывает; новая точка крепления — по OWN-18 (ведущая разрешает строку).

**Почему.** Мод, описанный дважды, чинят в одном месте и ломают в другом: Useful Idiots, txr_mines, tasks_defense и
stalker_ceasefire описаны дважды, это ~2,4 тыс. строк в srv. Когда мод разнесён по файлам, порядок обёрток задаётся
порядком загрузки, и его никто не видит. Владелец: адаптер нужен, чтобы после обновления мода «встать на то же место»
(ТЗ §6.33), и при этом никто не пишет своих прослоек (ТЗ §6.35). Поэтому обёртка — это крепление к моду, а не способ
делать механику.

**Плохо:**
- `coop_srv_factions_gamma.script:14` `CEASEFIRE_BLACKLIST` и `apply_ceasefire` повторяют stalker_ceasefire из G.A.M.M.A.
  только для Сервера;
- AGDD Voiced Actor живёт в трёх файлах: `coop_mods_misc.script:1160`, `coop_mods_actor_voice.script:201`,
  `coop_mods_voice_fx.script:195`;
- WPO живёт в `coop_mods_mags.script`;
- `coop_mods_presence_gamma.script` назван по сборке и обслуживает несколько модов (`drx_da_main`,
  `tb_rf_receiver_packages`, `tasks_mystery_of_the_swamps`, `nta_utils`); в нём свои глаголы `C().on(RF_FACT, …)` (:250),

### MOD-4. Мод пишется один раз; своих прослоек нет (Р111)

### CPP-7. Замок короткий и один на ресурс
**Правило.** Замок держат только на время работы с общим контейнером. Под замком копируют или меняют местами нужное, а

**Плохо:** `xrGame/GameObject.cpp:1071` и `xrGame/script_binder.cpp:80` — у каждого свой `static std::mutex s_stack_lock;`

**Хорошо:** `xrGame/coop/coop_events.cpp` `host_flush`: под `g_lock` делается только swap контейнеров, рассылка идёт после.

### CPP-17. Новое сообщение протокола

тела — `xrCoop/srv/coop_levels_wire.h`), а не новым `Msg`. Журнал несёт все факты кадра сервера карты по порядку, и сервер
мира читает пакет целиком (BUG-9). Отдельный `Msg` для такого факта — только решением ведущей.

Новый `Msg` добавляется целиком, в одном коммите:
1. значение в `enum class Msg` — только в конец своего диапазона: значения — часть провода, «append only»;
2. отправитель в `msg_sender` (`xrCoop/coop_protocol.cpp`) — явная строка: `HostOnly`, `ClientOnly`, `TrunkOnly` или
   `Either` с причиной. Забытая строка падает в `return MsgSender::Either;` в конце функции, и сообщение примут от любого
   пира;
3. имя в `msg_name`;
4. полоса (`Lane`) выбрана явно: зависимые сообщения — на одной упорядоченной полосе;
5. структура провода с `write()` / `read()`, где `read()` не берёт ничего, чему не может проверить границу;
6. обработчик в таблице режима и строка в `tests/test_handler_tables.cpp`;
7. подъём `kProtocolVersion` (CPP-4), золотые байты (CPP-5), тест «то же сообщение дважды = одно действие» (BUG-8).

**Почему.** Сообщение без строки в `msg_sender` открыто изменённому клиенту, а отдельный `Msg` для факта карты обгоняет
факты того же кадра в журнале.

**Плохо:** умолчание, которое правило закрывает: `msg_sender` (`xrCoop/coop_protocol.cpp:315`) кончается
`return MsgSender::Either;`, а `tests/test_handler_tables.cpp` (`table_problems`) принимает `Either` на обеих сторонах, поэтому
забытая строка проходит тест.

**Хорошо:** `Msg::LevelJournal = 0x01E0` — один упорядоченный путь фактов сервера карты; `case Msg::MapServerState: return
MsgSender::TrunkOnly;`.

**Проверка:** будет: в `tests/test_handler_tables.cpp` — «у каждого значения `Msg` есть своя строка `msg_sender` и имя в
`msg_name`» (пакет P8); ревью по списку.

### CPP-18. Сбой виден в месте сбоя
**Правило.** Обнаружив порчу состояния (кучи, объекта, таблицы), код останавливается громко в месте обнаружения: `FATAL` /
`R_ASSERT` с причиной и значениями. Обход «утечь и записать строку» вместо падения ставится только решением, записанным в ТЗ
или развилке плана, со строкой журнала и счётчиком в статусе, и пересматривается по данным стенда.

**Почему.** Тихий обход прячет порчу: причина уходит, а падение случается позже в чужом месте.

**Плохо / оставлено решением:** `ModelPool` `abandon_damaged` — утечка с записью вместо падения; оставлен развилкой №9 плана
Р107 до проверки по прогонам стенда.

**Хорошо:** `xrCore/gpu_device_lost.h` + `xrDebug::set_device_lost_note` — FATAL называет причину (BUG-21).

**Проверка:** ревью.

### CPP-19. Движок даёт общие методы
**Правило.** Движок даёт общие методы, без знания о конкретном меню, окне или стиле (решение владельца 2026-10-30). Если X-Ray
чего-то не умеет, в движок добавляют общий метод, а не обходят ограничение костылём в Lua. Для модов то же правило —
MOD-1.

**Почему.** Метод под одно меню не годится следующему и тянет знание интерфейса в движок, а костыль в Lua повторяет то,
что движок сделал бы одной функцией.

**Хорошо:** `xrCoop/coop_lua_fn.h` `luafn::call` — один общий способ позвать Lua из C++ для любого модуля.

**Проверка:** ревью: «назовёт ли этот метод следующий пользователь, не зная нашего меню?».

### LUA-3. Общее состояние — через движок
**Правило.** Синхронизация, репликация и авторитет — в движке. Lua — это клей к стоковой логике, интерфейс и совместимость
модов. Работающее на Lua ради переноса в движок не переписывают (Р16). Но новое общее длительное состояние идёт только через
движок: `coop.sync` (области `world` / `session` / `player` / `object`, `request` / `handler`, `on_change`) или новый механизм
C++. Это касается зеркала заданий, партии, гида, счётчиков найма, данных мира мода.

Новых протоколов на `send_event` / `coop_mods_core.publish` не пишут: никаких дайджест-списков, переотправки при входе и своих
таблиц «кому уже сказали». Своих кодеков тоже нет: кодек один, `coop_main.encode` / `decode` (объединение трёх кодеков — P35).
Не хватает области `coop.sync` — это задача движку, а не повод для своего протокола (OWN-18). Если что-то всё же
публикуется, то только при изменении. Смена формата провода или сохранения включает миграцию уже сохранённых строк.

Что надо знать о `coop.sync` (`xrCoop/coop_syncstore.h`):

| Область | Кто пишет | Где живёт | Предел |
|---|---|---|---|
| `world` | только решающий мира (`decides_world`) | в сохранении мира | 4 МиБ |
| `session` | только решающий мира | до конца сессии | 1 МиБ |
| `player` | сам игрок или решающий мира; ключ — дайджест ключа игрока, а не номер пира | в сохранении мира | 1 МиБ |
| `object` | решающий мира или владелец объекта; id — в нумерации хоста (BUG-4) | пока жив объект | 64 КиБ |

Одно значение — до 16 КиБ в закодированном виде. Сервер карты для хранилища — клиент: `net::client()` = «сессия идёт и
мир решаю не я» (`xrGame/coop/coop_net.h:52`). Поэтому `set` сервера карты в `world` и `session` получает отказ
`NotAllowed`. Факт карты для мира идёт не через `coop.sync`, а по таблице ниже.

Доставка в Lua — только эти пути:

| Путь | Что везёт | Статус |
|---|---|---|
| `coop.sync` `set` / `get` / `on_change` | общее длительное состояние от решающего мира | путь для нового состояния |
| `coop_mode.on_level_request(name, fn, door)` | запрос игрока решающему его карты: слой режима говорит «здесь / передай / брось» | разрешено |
| `coop_mode.share_up` / `share_down(name, get, set, every)` | таблица от сервера карты серверу мира и обратно; `every` — период опроса | разрешено; период — не чаще, чем нужно (BUG-19) |
| `coop_mode.publish(verb, t)` | разовое событие адресату, которого называет слой режима | разрешено в общих файлах для событий, не для состояния; в адаптерах — свой глагол (MOD-4) |
| `coop_mods_core.on` / `to_host` / `publish` / `send_big` и др. | свои сообщения адаптеров | долг MOD-4, только убывает |
| `api.send_event` напрямую | сырое событие | новых нет; в `coop_srv_*` сегодня есть — долг, потолок S29 |

Большое состояние (списки Hideout Furniture больше 12 КБ) идёт через `coop.sync` в пределах его областей, а не нарезкой и
переотправкой своими силами: у `send_event` предел 16 КиБ на сообщение (`xrGame/coop/coop_script.cpp:1044`). Не хватает
предела области — OWN-18.

**Почему.** Самодельная репликация повторяет то, что движок уже делает (поздний вход, пересинхронизация), и теряет случаи.
После 30.10 новое пошло на `send_event` в 21 скрипт вместо `coop.sync`.

**Плохо:** `coop_tasks.script:85-93` — свои события `coop_tl`, `coop_tl_list`, `coop_tl_req`, `coop_tv` … для зеркала
заданий; `coop_mods_hf.script:402-409` — обёртка `update_data` публикует `hf_data` на каждом обновлении без сравнения.

**Хорошо:** `coop_npc_stats.script:93` `coop.sync.on_change("object", KEY, on_change)`; вызовы `s.get(SCOPE, key)` /
`s.set(SCOPE, key, value)` в `coop_world_weather.script:51-60` — поздний вход и пересинхронизацию делает движок. Запасная
ветка `if not s then return nil end` там же — долг LUA-5, а свой `actor_on_update` (:284) — долг HOT-8.

**Проверка:** `будет: S29` (число скриптов с `send_event` — потолок, только вниз); `будет: L17` (новые глаголы в адаптерах);
ревью: «это состояние или событие? почему не `coop.sync`?».

### LUA-4. Видимость модуля
**Правило.** Глобалы модуля — это его публичный API, и туда попадает только то, что зовут другие скрипты. Приватная функция
объявляется `local`. Если её зовут выше места определения, она заранее объявляется как `local f`, а присваивается ниже, а не
выставляется глобалом. Предел 200 локалей — сигнал делить файл по обязанностям (OWN-14), а не прятать помощников в таблицы
`host` / `ops` и в глобалы.

**Почему.** Глобал ради доступа и таблицы ради обхода предела локалей превращают внутренности модуля в API, который начинают
звать другие файлы.

**Плохо:** `coop_main.script:1033` `env_own_cover = own_cover`; `coop_tasks.script:601-602` — помощники в таблицах модуля
«because the chunk is at Lua's limit of 200 locals».

**Хорошо:** `local own_cover` до `client_env_tick`, ниже — `own_cover = function(...) … end`.

**Проверка:** `lint:L7` (больше 190 локалей); `будет: S28` (глобал, которому присваивается уже объявленная `local`); ревью.

### LUA-5. Запасных веток для своего же пакета нет
**Правило.** Для того, что приходит в одном пакете с кодом, веток «модуль или экспорт отсутствует» не пишут: `coop_trust`,
`coop_tasks`, `coop_main` и другие зовутся прямо. Все пиры одной версии протокола (Hello, `build_id`), поэтому веток под
«клиента сборки 56» нет.

Ветка под старый exe пишется только для экспорта, который новее объявленной минимальной сборки exe для пакета «только
скрипты», и с причиной в строке. Минимальную сборку объявит и проверит `tools/package.ps1` (будет: пакет P2); после этого ветки
для более старых сборок удаляются (`coop.instrument`, `coop.zone_path`, `api.talk_recent`). Запасного опроса вместо события
движка нет.

**Почему.** Запасные ветки либо не выполняются, либо делают не то. `revive_poll` принимал резкое лечение за оживление и
снимал контузию BHS; ветка для сборки 56 ставила мину без предмета; `trust_pass` «на старой установке» пропускал всё.

**Плохо:** `coop_npc_world.script` — `pcall(function() return _G.coop_trust end)` «without that script (an older install)
the request goes through»; до правки F4 (мод `82206f06`): `coop_mods_core.script:769` `revive_poll` каждый кадр до первого
события движка.

**Хорошо:** прямой вызов `coop_trust.pass(name, ok, fmt, ...)`, потому что модуль приходит в том же пакете; оживление
узнаётся только по событию движка.

**Проверка:** `будет: S8` (`pcall(function() return _G.coop_` — отказ); ревью.

### LUA-7. Первая строка — метка слоя
**Правило.** Первая строка каждого `coop_*.script` и `modxml_coop_*.script` — метка слоя по `docs/MODES.md` §2. Для Ядра и

### LUA-8. Формат Lua
**Правило.** Один стиль Lua:
- отступ — табами;
- один оператор в строке: без цепочек через `;` и без `if … end` в хвосте строки рядом с другим вызовом;
- хвостовой комментарий без кодов работ.

Форматирует stylua по конфигу проекта (будет: `stylua.toml`, пакет P35). До него соблюдай три пункта выше.

**Почему.** Файл с отступом в 4 пробела среди табов и три оператора в одной строке читаются иначе, чем весь остальной код, и
прячут ветку.

### LUA-11. Интерфейс — только там, где играет человек
**Правило.** Окна, строки HUD и меню создаются только в процессе, где `coop_mode.actor_is_player()` верно. Сервер мира и

**Почему.** HUD на сервере мира тратит кадр на окна, которых никто не видит, а мировая логика в кадре HUD перестаёт
работать там, где HUD нет.

**Хорошо:** образец: `if not coop_mode.actor_is_player() then return end` первой строкой создания окна; мировое событие
шлёт модуль перехода, HUD подписан на его ответ.

**Проверка:** ревью; `будет: L14` (`api.is_player` в Ядре).

## 6. HOT — скорость

### HOT-1. Оптимизация только с замером и ничего не меняет для игрока
**Правило.** «Оптимизированный» значит: код на своих местах, работа разнесена по потокам, загрузки быстрее, FPS выше,
инструменты и библиотеки свежие. То, что игрок видит, слышит и чувствует, не меняется: ни задержки, ни тайминги, ни порядок,
ни позиции, ни решения ИИ, ни звук (принцип P14).

Оптимизация начинается с замера по протоколу пакета P0, отдельно для каждого режима:
- Кооп — хост и 2 клиента;
- Сервер — сервер мира, сервер карты и клиент;
- одно сохранение, людное место, 20 с прогрева, окно 150 с, 3 прогона.

В работу берут только то, что стоит больше ~0,1 мс за кадр или даёт пики. Начинать стоит с того, что уже пишется в журнал:
`texture loading time`, `[coop] content manifest … ms`, трафик по типам в `coop_status`. Задание на оптимизацию конкретное.
Слова «быстрее» и «оптимизировано» пишут только с цифрами до и после по одному протоколу, иначе — «не проверено».

Изменением поведения, а не оптимизацией, считаются: событие, заменённое таймером; кэш, который может устареть внутри своего
использования; троттлинг; перенос работы в другой кадр или в другой домен маршрута.

Кто мерит. Исполнитель не запускает игру, стенды и сборки (OWN-8), поэтому замер снимает ведущая (или агент стенда, которого
она запускает). Задание на оптимизацию приходит исполнителю с цифрами «до». Исполнитель сдаёт правку, пробу за `coop_debug`
для замера «после» и отчёт со словами «не проверено» до цифр ведущей. Задания без цифр «до» исполнитель не берёт (OWN-18).

**Почему.** Пример запрещённого от владельца: звук сводили в стерео на секунды вперёд, и при ходьбе он отставал от игрока.
Все горячие места ревью Р107 — оценки по коду. Единственный замер (2026-11-13) показал HUD 0,205 мс — его трогать незачем.

**Плохо:**
- предложение ревью гонять `watch_routes` из `coop_mods_item_state.script` по таймеру 0,5–1 с — сервер мира позже узнал бы о
  смене маршрута;
- предложение читать `mgr().now_ms()` один раз в `join::frame`: `host_board_step` может синхронно записать сейв, и
  следующие шаги получили бы время до записи.

**Хорошо:** `watch_routes` по событиям `coop_world_back` и смены карты; `coop_hud_markers.script:651-674`
`perf_start` / `perf_stop` — по этому замеру HUD исключён из работ.

**Проверка:** ревью: в отчёте пакета таблица «мс за кадр и вызовов в секунду» до и после по каждому режиму, плюс тесты обоих
режимов без изменений.

### HOT-2. Чем мерить
**Правило.** Движок профилируют сборкой ProfiledDX11 (Optick, `XRCORE_PROFILER`) только при закрытой игре владельца.
Сборка идёт в свой каталог вывода или в отдельное дерево; релизные бинарники откладываются в сторону. Бинарники кладут в
копию `bin` стенда — никогда в `game/`, `mo2/` или `E:\Programs\RayLink`. Сравнивают доли и разности по зонам, а не
абсолютные мс против Release-AVX: в ProfiledDX11 нет AVX и LTCG.

Зона движка ставится одной строкой `PROF_EVENT("coop <имя>")` со статическим именем; `PROF_EVENT_DYNAMIC` не используется.
Сверхчастые мелкие функции не размечаются: их цена = счётчик вызовов × микротест. Lua мерят через `profile_timer` за
выключателем `coop_debug` с печатью в `coop_status`.

**Почему.** `Common.props:20` даёт всем конфигурациям один `OutDir bin_dbg`, и ProfiledDX11 в том же дереве затирает
релизный `xrCore.dll`. Зона, которая дороже самой функции, искажает замер.

**Плохо:** `xrCore/profiler.h:21-23` — `PROF_EVENT_DYNAMIC` создаёт описание на каждом проходе.

**Хорошо:** `xrGame/coop/srv/coop_mapserver_stats.cpp:141-151` — строка «frame parts» из `Device.Statistic`;
`coop_hud_markers.script:651` `perf_start` через `rawget(_G, "profile_timer")`.

**Проверка:** `будет: S14` (`PROF_EVENT_DYNAMIC` вне `xrCore/profiler.h` — запрет); ревью.

### HOT-3. Когда работы нет, кадр ничего не стоит
**Правило.** Когда делать нечего, кадр и тик ничего не стоят. Первой идёт самая дешёвая проверка: пусто ли в очередях, есть
ли получатель, включена ли диагностика, локальный флаг, окно таймера, `next(t)`, совпадает ли id со своим актором. Только
после неё идут выделение памяти, замок, сборка сообщения, вызовы движка (`api.*`, `coop_mode.*`, `C().active()`), `pcall` и
поиск объектов. Проверка, которая не меняется внутри цикла (режим, флаг, роль, `data()`, имя уровня), выносится над циклом.
В колбэке на каждый объект (`npc_on_update`) цикла нет: такой ответ читается один раз за кадр у его владельца (HOT-7), а не
спрашивается заново для каждого NPC. Не считай и не отправляй то, что никто не примет. То, что обязано выполниться в первом
кадре, — отдельная ветка до таймера.

Дешёвая проверка стоит в обработчике (или в его регистрации), которому принадлежит работа, а не в обёртке, общей для
нескольких обработчиков: такая проверка выключит и чужие обработчики.

**Почему.** Каждый вопрос фасада стоит 4–9 `pcall` в движок, а в горячем месте он умножается на число NPC, предметов или
маркеров в кадре. Холостой кадр хоста строит и рушит две карты и множество.

**Плохо:**
- `xrGame/coop/coop_events.cpp` `host_flush` объявляет `xr_map`, `xr_map`, `xr_set` каждый кадр, даже пустой;
- `coop_mods_xchg_fdda.script:180` `if C().active() and not self.first_update then` — движок спрашивают на каждом обновлении
  каждого устройства;
- `coop_mods_misc.script:1077` `pcall(function() …health…)` до проверки окна `DRAIN_MS`;
- предложение ревью поставить `next(mines)` в общий `guard()` `coop_npc_world.script`: он нужен и `on_container_opened`,
  который тогда перестал бы работать без мин.

**Хорошо:** `xrGame/coop/coop_story.cpp:3431-3433` `if (!spot_replicable(ml, spot_type)) return;` до `Writer w(48);`;
`coop_npc_player_checks.script:368-369` `if now < next_check then return end` до всей работы (сама регистрация этого кадра —
долг HOT-8).

**Проверка:** ревью (чек-лист горячего пути); `будет: S4` (первый оператор обработчика кадра — вызов `api.`, `coop_mode.` или
`C().` — предупреждение с потолком); замер HOT-1.

### HOT-4. На горячем пути не выделяют память и не копируют
**Правило.** На горячем пути (кадр, тик снимков, каждое сообщение, каждый NPC или предмет) нет выделений и копий.
- **C++.** Список игроков обходят через вид сессии без копии (будет: `Session::for_each_joined`, пакеты P3/P8). Чужую структуру
  передают по константной ссылке; при последнем использовании — `std::move`. `Writer`, векторы целей и списки — член класса
  или статический scratch с `clear()`, который сохраняет ёмкость. На всех адресатов один ENet-пакет; один
  `collect_players` за кадр. Сравнивай с прошлым состоянием до копирования и сортировки.
- **Lua.** Нет `pcall(function() … end)` — только `pcall(f, a, b)`. Нет новых таблиц, замыканий, `vector2`, `CTime` и строк на
  каждый вызов. Переиспользуются поля модуля, общая пустая таблица и кэш по ключу-идентичности. Значение по умолчанию —
  константа модуля, а не `or { 20, 10 }`. Переиспользуемая запись не живёт через вложенный вызов того же кода.

**Почему.** Сборщик мусора LuaJIT платит за каждую мелочь кадром (в `coop_*.script` 835 `pcall(function`). Аллокатор
движка обнуляет каждый блок. `Session::peers()` строит новый вектор со строками на каждую рассылку.

**Плохо:**
- `xrGame/coop/hostplay/coop_hostplay_mode.cpp:62` `for (const PeerInfo& p : s.peers())` на каждую рассылку;
- `xrGame/coop/coop_entities.cpp` `Writer entry(128);` на каждое существо каждые 66 мс;
- `coop_hud_revive.script:200` `pcall(function() return api.is_active() and … end)` на каждый `actor_on_update`;
- `coop_mods_item_state.script:1100-1107` `capture_inventory` — новое замыкание и захват каждого предмета каждый кадр.

**Хорошо:** `coop_npc_logic.script:559-570` `has_actor_conds` — вердикт кэшируется по идентичности `st.logic`, без выделений.

**Проверка:** `будет: S4` (`pcall(function` и `{` в функциях обработчиков кадра — отказ для новых, потолок по файлу); `будет:
S23` (`.peers()` в `xrGame/coop` — потолок); ревью.

### HOT-5. Без строк и линейных поисков на каждый вызов
**Правило.** На каждый вызов, объект или кадр не строят строки (`std::string`, `shared_str`, `xr_sprintf` ради ключа или
перевода) и не сравнивают секцию через `xr_strcmp`, если есть закреплённая `shared_str`. Нет линейных поисков и пересборки
карты. Вместо этого:
- ответ кэшируется по имени или указателю;
- объект находят один раз за кадр и передают дальше;
- неудачу запоминают до изменения;
- дубли проверяют сортировкой или битсетом, а не за O(N²).

**Почему.** Шлюз вызовов делает 1–2 аллокации и линейные поиски под замком на каждый вызов, а сверка заданий пересобирает
карту 5 раз в секунду.

**Плохо:** `xrCoop/coop_calls.h:1691` `Classes::class_of` → `detail::lowered(name)` на каждый gated-вызов;
`xrGame/coop/coop_sync.cpp:390` — сравнение строки секции дважды на существо за кадр.

**Хорошо:** `xrGame/coop/coop_world.cpp:24-29` — секция закрепляется один раз («a section compare is then a pointer
compare»).

**Проверка:** ревью; замер HOT-1.

### HOT-6. Без полных проходов по таймеру
**Правило.** Не обходи все объекты уровня (`Level().Objects`) или весь реестр ALife по таймеру, если ответ даёт реестр,
который ведут хуки появления и удаления. В Lua повторных полных проходов тоже нет: например, обход всех мин для каждого
игрока внутри цикла по минам, весь pstor каждые 0,5 с, весь рюкзак каждый кадр, все id 1..65534 на каждый запрос.
Работа идёт по изменению:
- грязные ключи от всех писателей;
- дешёвая подпись (число + хэш id) перед перестройкой;
- один проход на игрока;
- `distance_to_sqr` с квадратом радиуса.

Разобранный пакет второй раз не разбирают. Обход ради диагностики — только за выключателем (OWN-17).

**Почему.** Такие проходы стоят квадратично от числа объектов, хотя почти ничего не меняется. Кэш, который знает не всех
писателей, теряет изменения.

**Плохо:** `xrGame/coop/coop_entities.cpp` и `xrGame/coop/coop_objects.cpp` —
`for (u32 i = 0, n = Level().Objects.o_count(); i < n; ++i)` каждые 66 мс; `coop_npc_world.script:356` — для каждого
игрока `near_mine(p)`, который снова обходит все мины с `distance_to`.

**Хорошо:** один проход на игрока с `distance_to_sqr(pos) <= TRIGGER_R2`; будет: реестр id существ, который пополняет
`remote::on_net_spawn` и чистит удаление (пакеты P12/P13, после замера).

**Проверка:** ревью: «сколько раз в секунду × на сколько объектов? кто ещё пишет это состояние?»; `будет: S35`
(`Level().Objects.o_count()` в `xrGame/coop` — потолок).

### HOT-7. Кэш: один на кадр, сброс по каждому входу; общий список только читают
**Правило.** Список игроков и ответы о ролях берут из одного кадрового кэша, а не строят на месте:
- список — `coop_npc_players.others()` / `everyone()` / `peer_of` (есть, обновляется раз за `time_global`);
- ответы без аргументов — из кэша фасада (будет: P24 — кэш на кадр со сбросом по счётчику поколения движка; P27 —
  `host_on()` / `roles()`);
- вопросы с аргументами (`where`, `decider`, `writes`) дольше кадра не кэшируются.

До пакета P24 единственный кадровый кэш Lua — `coop_npc_players.refresh()`. Нужен ещё один ответ без аргументов на кадр (роль,
флаг сессии) — его добавляют полем туда, правкой модуля-владельца, а не своей таблицей «на этот кадр» в своём файле.

Кэш сбрасывается событием, которое меняет любой из его входов. Список входов и событие сброса пишутся в комментарии у кэша.
Кэш не переносит в другой кадр работу, которую вопрос делает попутно. Общий список только читают: кто сортирует или меняет,
сначала копирует. Запрещены `pcall(api.players)` в цикле, второй свой кадровый кэш и свой таймер `host_on` в каждом файле.

**Почему.** Один и тот же список строится десятки раз в секунду. Устаревший кэш меняет, кто решает и кто ведёт существо, — а
это изменение поведения. Сортировка общего списка на месте переставила бы его для всех читателей кадра.

**Плохо:** `coop_core_chat.script:220-221` `table.sort(list, …)` по результату `players()`;
`coop_npc_compat.script:1290` — предикат `P.host_with_clients()` на каждом NPC в каждом хуке; `coop_mode.script` `current()`
попутно запускает `run_pending()` у `when_srv`, и наивный кэш перенёс бы эту работу.

**Хорошо:** `coop_npc_players.script:150-153` `refresh()` — `if now == cache_at then return end`, список строится один раз за
кадр.

**Проверка:** `будет: S6` (`api.players(` вне `coop_npc_players` — потолок; `table.sort(` над общим списком без копии —
отказ); ревью: у нового кэша есть список входов и событие сброса.

### HOT-8. Колбэки регистрируются только на время работы
**Правило.** Колбэк на каждый объект (`npc_on_update`, `monster_on_update`) регистрируется, только пока есть работа, и
снимается, когда работы нет. Регистрацию включает и выключает та запись, которая создаёт первую работу или убирает последнюю
(тот же вызов, что кладёт запись в таблицу или удаляет её), а не опрос по таймеру. Разовая работа выполняется в
`actor_on_first_update` или снимает себя `UnregisterScriptCallback`. Если у работы есть событие (конец сессии, смена
маршрута, перенос предмета, смерть), её подписывают на событие, а не опрашивают каждый кадр.

Периодическая работа. `actor_on_update`, `CreateTimeEvent`, `AddUniqueCall` и `Update()` окна — одинаково периодическая
работа, и их число не растёт (сегодня в `coop_*.script` 128 регистраций `actor_on_update`, 116 `CreateTimeEvent` и 11
`AddUniqueCall`). Служба тиков (по одной на домен маршрута) будет в пакете P24. До неё новая периодическая работа встаёт в уже
зарегистрированный кадр модуля-владельца своего дела — вызовом из его тика со своим окном таймера. Нет такого владельца —
OWN-18: ведущая разрешает строку долга в потолке S5 или поднимает P24.

**Почему.** Каждая регистрация каждый кадр стоит обёртку маршрутизатора и вызов Lua, даже если внутри стоит 250-мс таймер.
Разовые обработчики висят всю сессию. Включение по опросу запаздывает до периода опроса: это перенос работы, то есть
изменение поведения (HOT-1).

**Плохо:**
- `coop_mods_nta.script:482-484` `npc_on_update` для Mirage на всю сессию;
- `coop_mods_perks.script:436-441` — разовый обработчик остаётся зарегистрированным;
- `coop_npc_player_checks.script:366-380` — новый анонимный `actor_on_update`, который раз в 250 мс опрашивает `next(data())`,
  чтобы включить или выключить `npc_on_update`;
- `coop_world_weather.script:284` — свой `actor_on_update` с тиком 1 с.

**Хорошо:** `coop_mods_misc.script:125-127` `await_session` снимает себя, как только работа сделана; образец включения по
записи: `RegisterScriptCallback("npc_on_update", f)` в функции, которая кладёт в таблицу работы первую запись, и
`UnregisterScriptCallback` там, где удаляется последняя.

**Проверка:** `будет: S5` (`RegisterScriptCallback("actor_on_update"`, `CreateTimeEvent(`, `AddUniqueCall(` — потолки;
постоянные `npc_on_update` / `monster_on_update` — потолок).

### HOT-9. Горячий интерфейс Lua ↔ движок
**Правило.** Функция движка, которую Lua зовёт на горячем пути, регистрируется raw `lua_CFunction` (`register_raw` в
`xrGame/coop/coop_script.cpp`), а не luabind `def()`. Обёртка решает всё постоянное в момент оборачивания (домены `owner` и
`view` выполняются всегда), а на каждый вызов делает только переменную часть. Счётчики копятся в Lua и сдаются движку
пачкой. Путь на каждый вызов идёт без замка (атомарный флаг, кэш слота с поколением) и без строк, которые потом выбрасываются.

**Почему.** Пять самых частых предикатов (`is_active` — 98 мест вызова) идут через luabind. Маршрутизатор на каждый вызов
каждого обработчика G.A.M.M.A. делает два вызова движка под замком, хотя для `owner` и `view` ответ всегда «да».

**Плохо:** `xrGame/coop/coop_script.cpp:2377` `def("is_active", &coop::script::l_is_active)`; `xrGame/coop/coop_router.cpp`
`runs` + `note` под `g_lock` на каждый вызов.

**Хорошо:** `xrGame/coop/coop_script.cpp:2021` `void register_raw(lua_State* L)` — остальной `coop.*` уже raw C.

**Проверка:** ревью; микротест luabind против raw на стенде (HOT-2).

### HOT-10. Трафик
**Правило.** Состояние реплицируется при изменении: одинаковый пакет подряд не шлётся (это нейтрально). Троттлинг по времени
или по порогу изменения — это изменение поведения (HOT-1). До правки трафика снимают байты в секунду по типам сообщений из
`coop_status` на одном сценарии, после правки — то же самое.

**Почему.** Лампы HF шлют `hf_data` на каждом обновлении биндера одинаковыми пакетами всем игрокам.

**Плохо:** `coop_mods_hf.script:402-409` — `hf_data` уходит на каждом обновлении биндера.

**Хорошо:** `xrGame/coop/coop_console.cpp:123` `coop_status` — «traffic by message type»: готовый замер до и после.

**Проверка:** ревью; замер трафика по типам.

## 7. BUG — классы ошибок

Каждое правило ниже — класс ошибок, который уже случался. Как правило, найдено несколько случаев (ТЗ §6, находки Р107).

### BUG-1. Решает один процесс
**Правило.** У каждого запроса, значения и объекта ровно один процесс, который решает и отвечает:
- в Коопе — хост;
- в Сервере — сервер карты для своей карты и своих отрядов, всё остальное — сервер мира.

Это уточнение принципа P1 («хост авторитетен») для двух видов процессов Сервера; таблица ответов — `docs/MODES.md` §4.

Остальные процессы пересылают запрос ему, а не исполняют сами. Всё, что должно совпадать на всех машинах, решающий передаёт
синхронизацией движка (принцип P1). Кто отвечает, задаёт одна чистая функция в `xrCoop/*_rules.h` или вопрос фасада
(`coop_mode.decider(peer)`, `writes(id)`), одинаковый для создания и удаления. Одно значение за кадр пишет один код: здоровье,
звук ранения, реплика.

Кто пишет объект — правило одного писателя `xrCoop/coop_writer_rules.h`: писатель читается по корню объекта (`root_of`), и
каждый режим отвечает `Mode::writer_of` по своим таблицам (кто ведёт карту, кто держит отряд). Предмет в инвентаре пишет
писатель корня цепочки держателей (персонаж игрока, отряд NPC); вещь на земле — ведущий её карты. Писатель меняется только на
заборе (`fence_admits`), значит и переход предмета с карты на карту не меняет писателя мимо забора. В Lua тот же ответ даёт
`coop_mode.writes(id)`.

**Почему.** Два ответчика дают два разных ответа, и получатель берёт не тот. Два писателя одного значения перетягивают его
каждый кадр.

**Плохо:** до правки Р99 на `StateDumpRequest` отвечали и сервер мира, и сервер карты, каждый своей меткой; создание от
сервера карты принималось на любой карте, а удаление — только на своей (ТЗ §6.9).

**Хорошо:** `xrCoop/srv/coop_mapserver_rules.h:391` `answered_by_his_map_server(Msg type)` + `route_incoming` — отвечает только
сервер карты игрока; тест `tests/test_srv_repair_answer.cpp`.

**Проверка:** `test:` нативный тест правила под каждым видом процесса `MODE_CASES` — отвечает ровно один; ревью: в описании
правки есть строка «кто решает» по каждому режиму.

### BUG-2. Номер объекта не освобождается и не занимается в одном кадре
**Правило.** На одной машине номер объекта не освобождают и не занимают заново в одном кадре. Появление под номером, который
ещё держит уходящий объект (`getDestroy()`), возвращается в очередь на следующий кадр — с пределом кадров, после него в журнал
идёт «не создан». Номер из собственного диапазона процесса (`kLeaderIdFirst = 0x9000`, `xrCoop/srv/coop_levels_keeper.h`) не
уходит другому процессу, пока тот не получил появление этого объекта. У каждого диапазона один генератор номеров. Порядок
выдачи генератора (подряд или через один, с какого номера) закреплён нативным тестом, и комментарий говорит то же, что тест.

**Почему.** Стоковый `net_Spawn` отказывает занятому номеру, и мягкий путь разбирает недостроенного сталкера: порча кучи и
вылет без FATAL. Номер, которого получатель не знает, превращается в отказ «no such object» на каждом сообщении.

**Плохо:** до правки Р104 `client_spawn_allowed` не считал занятым номер объекта «на удалении»: GE_DESTROY и M_SPAWN сталкера
19468 пришли в одном кадре; `Mode::own_free_id` слоя Сервер берёт номера пула через один, а его комментарий говорит другое
(ТЗ §6.32, побочная находка).

**Хорошо:** `xrCoop/coop_spawn_wait_rules.h` `spawn_wait::decide(...)` → `Verdict::Wait`, `kMaxWaitFrames = 30`; тест
`tests/test_spawn_wait_rules.cpp`.

**Проверка:** `test:` «удаление и появление одного номера в одном кадре» под `MODE_CASES`; стенд: 0 строк
`Object with ID already exists` и `no such object` (BUG-22).

### BUG-3. Метки и удостоверения сравнивают по общему правилу
**Правило.** Метку, поколение, хэш или другое «удостоверение» объекта, которое каждый процесс вычисляет сам, побайтно между
процессами не сравнивают. Есть два правильных пути:
- одно правило равенства в Ядре для всех (`same_item`: то же имя и тот же host id);
- получатель перенимает метку того, кто создал объект.

Решение, которое каждая машина принимает сама, строят только из данных, одинаковых на всех машинах (all.spawn, конфиги,
сообщённый факт), а не из своей истории.

**Почему.** У разных процессов метки разные. Строгое сравнение отклоняет честные данные, и таблица деталей или подбор с трупа
не доходят никогда.

**Плохо:** `xrCoop/coop_replacement.h:69` `token()` = `source_name + "/" + target + "/" + nonce` — у сервера мира и сервера
карты разные метки одного ствола, поэтому `coop_economy_mdata.on_se` отклонял таблицу деталей.

**Хорошо:** `coop_economy_mdata.script:140` `function same_item(a, b, hid)`; `xrCoop/coop_player_touch_rules.h`
`near_spawn` — места прибытия из all.spawn, одинаковые у всех машин.

**Проверка:** `test:` Lua-тест двух процессов с разными метками одного предмета (`tests/lua/test_srv_rider_stamp.lua`,
`tests/lua/test_hostplay_rider_stamp.lua`); ревью: «кто вычисляет эту метку и совпадает ли она у всех процессов?».

### BUG-4. Узнавать по устойчивому ключу
**Правило.** Игрока узнают по номеру, который даёт движок (`from`, `api.self_id()`, `avatar_id`, `peer_of_avatar`), объект —
по id, зону и точку мира — по имени. Не по нику, не по позиции в списке («первая или последняя зона этого типа») и не по
указателю на объект, который могут удалить. Ник используют только для показа и как запасной путь, когда номера нет.

Нумерации id две: своя у каждой машины и нумерация хоста (у клиента отличается пара «актёр / свой двойник»), а у сервера
карты есть ещё свой диапазон (`kLeaderIdFirst = 0x9000`). На проводе, в `coop.sync` и в сохранённом или общем состоянии объект
называется номером в нумерации хоста. Переводят только на границе: C++ — `join::to_host` / `join::to_local`, Lua —
`coop_mods_core.hid` / `lid` (в общих файлах — до `coop_util`, LUA-1).

**Почему.** Ники совпадают и меняются: строка чужого игрока с моим ником рисовалась как своя. Арена брала последнюю
`[arena_zone]` Бара (клетку) вместо ямы.

**Плохо:** до правки F9 (мод `82206f06`): `coop_core_chat.script:199` `local kind = (me and nick == me) and "self" or "other"` —
хотя `on_line` получает `from`.

**Хорошо:** `coop_core_chat.script:201-206` — своя строка по `from == call("self_id")`, ник только когда `from` нет; арена —
только зона `bar_arena`, по имени.

**Проверка:** `будет: S24` (сравнение с ником — предупреждение с потолком); `test:` чат с двумя одинаковыми никами.

### BUG-5. Если применить нельзя — отложи, а не выбрасывай
**Правило.** Если получатель не может применить или сохранить пришедшее прямо сейчас (нет объекта, нет `client_data`, чужая
метка, исчерпан бюджет кадра), он откладывает это: в очередь на следующий кадр или до следующего появления вещи. У отложенного
есть предел и счётчик. Бюджет кадра переносит остаток на следующий кадр в прежнем порядке. Если отказ всё же нужен, он уходит
отправителю, чтобы тот повторил. Молча уничтожать хвост очереди или вытеснять старое без счётчика нельзя. Предел, при
котором выбрасывается только что добавленное, — ошибка.

**Почему.** Отказ без ответа и выброс без счётчика теряют состояние навсегда: отправитель считает, что всё дошло, а журнал
молчит.

**Плохо:** до правки F5 (движок `bd4d1cf77`): `xrGame/coop/coop_sound.cpp` — Lua-события звука сверх 32 за кадр
уничтожались без счёта; до правки F10 (мод `82206f06`): `coop_debug_ui.script:272` `while #list > 200 do table.remove(list)
end` после вставки удалял только что добавленную звезду.

**Хорошо:** `xrCoop/coop_frame_queue.h` (правка F5, движок `4dd9c6aeb`) — хвост сверх бюджета кадра ждёт следующего кадра в
прежнем порядке, потери считаются; `xrGame/coop/coop_items.cpp:289` `g_staged_uses` + `apply_staged_uses()` — порции, которые
сервер мира не может хранить, ждут следующего появления вещи, счётчик `uses staged` в статусе.

**Проверка:** `test:` тест переполнения: хвост остаётся впереди новых, потери считаются в статусе; стенд: 0 строк
`cannot be stored`.

### BUG-6. У растущей таблицы есть предел и владелец
**Правило.** Каждая таблица, множество или очередь, которые растут со временем сессии, числом пиров, объектов или сообщений,
имеют записанный предел и владельца, который чистит их в конце сессии. У состояния по игроку есть путь удаления при его
уходе, у состояния по объекту — при удалении объекта. Через кадры хранят id, а не `game_object`. Каждый предел считает
выброшенное в строке статуса и пишет первую потерю. «Писать один раз» — это бюджет по времени со счётчиком (`Ledger`), а не
множество ключей навсегда.

**Почему.** Вечное множество на сервере мира растёт с каждым переподключением и глушит те же строки в следующих сессиях.
`game_object`, сохранённый на 250 мс, после смены аватара становится устаревшим.

**Плохо:** `xrCoop/coop_session.cpp:274` `std::set<std::string> m_logged_once;` — `hard_stop()` его не чистит;
`coop_mods_core.script:395-400` `buckets[k]` по ключу `from:verb` не удаляется никогда.

**Хорошо:** `xrCoop/coop_lua_errors.h` `Ledger` — `kRepeatMs`, не больше `kMaxPlaces` мест; `coop_mods_nta.script:485`
`npc_on_net_destroy` удаляет запись по id вместе с объектом.

**Проверка:** ревью: «где удаляется эта запись?»; `test:` «игрок входит и выходит N раз — размер таблиц не растёт»; «стоп →
старт» — первая строка снова пишется.

### BUG-7. Конец сессии и прерванные машины состояний
**Правило.** Состояние сессии (паузы, ожидания, счётчики, бюджеты строк, книги ожиданий) живёт в модуле и сбрасывается его
`reset()` из единого списка сброса (CPP-12). Через этот сброс проходит каждый путь конца: свой `stop`, отключение,
`hard_stop`, загрузка нового мира. Всё, что держит устройство или глобальный флаг (пауза «хост молчит»), снимается в
`Manager::set_phase(Off)` или в общем teardown. Function-static счётчиков, переживающих сессию, нет. У машины состояний (сбор
арены, история у костра) есть выход для каждого прерывания — участник ушёл, умер, вышел из мира. Этот выход возвращает
машину в покой, а не запускает действие.

**Почему.** Забытый путь конца оставляет паузу до следующей сессии. Прерванный сбор арены уносил в бой одного игрока без его
согласия.

**Плохо:** до правки F6 (движок `4dd9c6aeb`): `xrGame/coop/coop_manager.cpp:575` `Manager::stop()` без `host_silence_off` — его
снимал только путь отключения.

**Хорошо:** `entities::reset()` (`xrGame/coop/coop_entities.cpp`) обнуляет книги и бюджеты строк копий;
`xrGame/coop/coop_manager.cpp:228` — `Manager::set_phase(Off)` снимает паузу «хост молчит» для любого пути конца (правка F6);
`coop_newgame_leftover.script` стирает остаток `[character_creation]` при каждой загрузке.

**Проверка:** `test:` на каждый путь конца (stop, disconnect, hard_stop, load) — состояние сессии пусто; для машины состояний —
тест каждого прерывания.

### BUG-8. Повтор — это одно действие
**Правило.** Каждое сообщение, которое может прийти повторно (повторная отправка, переподключение, пара offline → online в
одном приёме, повторная доставка настроек, уход игрока), применяется идемпотентно. Повтор того же значения узнаётся как
повтор раньше проверки писателя и раньше побочных действий. Операция, которая тратит или платит, исполняется один раз — по
номеру операции (`coop_mode.op_done(op, answer)`), а не по окну времени.

**Почему.** Повтор, принятый за изменение, даёт отказ «not the writer», перезапуск уроков или вторую выдачу. Окно «второй раз
за 3 с» пропускает повтор через 4 с и режет честную операцию внутри 3 с.

**Плохо:** при уходе игрока сервер карты отдавал и тут же забирал каждую вещь персонажа, а в конце кадра слал Parent «в того
же держателя» — ~100 отказов `not the writer` на каждый уход (ТЗ §6.32).

**Хорошо:** `xrCoop/srv/coop_levels_accept.h:122` `unchanged_parent(parent_here, to)` — Parent в того же держателя считается
повтором до проверки писателя; тест `tests/test_levels_accept.cpp` `accept_unchanged_parent_is_a_repeat`.

### BUG-9. Порядок сообщений и готовность
**Правило.** Сообщения, которые зависят друг от друга, идут одним упорядоченным путём, и получатель применяет их в порядке
решающего. Смена фазы (переход между картами, остановка карты, сохранение мира) ждёт «забора»: пока получатель не подтвердит
всё отправленное. Обработчик не читает данные раньше готовности (настройки, снимки, мир) — он ждёт события «готово». Копия
ставит флаг состояния только после того, как сама дошла до этого состояния.

**Почему.** Новая настройка раньше старой или флаг «оружие повешено» раньше, чем пистолет убран из руки, дают состояние,
которого нет у решающего.

**Плохо:** до правки Р71 копия ставила флаг «оружие повешено» раньше, чем убирала пистолет, и NPC «играл на пистолете» у
костра.

**Хорошо:** `xrCoop/coop_hands_rules.h` — флаг «повешено» ставится только тогда, когда в руке у копии то самое оружие; тест
`tests/test_hands_rules.cpp`.

**Проверка:** `test:` «два сообщения в обратном порядке» и «фаза меняется, пока сообщение в пути»; ревью.

### BUG-10. Операция проводится целиком: сначала проверка, потом исполнение

решающий, потом исполняет по принципу «всё или ничего». Копия не двигает у себя вещи и деньги и не списывает предмет до

**Проверка:** `test:` «решающий отказал — у клиента ничего не изменилось» (`tests/tools/test_trade_delivery.py`); ревью:
порядок «проверка → исполнение → последствия».

### BUG-13. Состояние едет вместе с объектом
**Правило.** Состояние, которое мод или наш код держат на объекте (заряды, детали WPO, износ, апгрейды, обвесы, клин,

**Проверка:** `test:` «предмет перешёл к другому процессу — состояние то же» под `srv_world` / `srv_map` / `hostplay`; стенд:
`tools/stand/ms_crash_server.ps1`, `tools/stand/save_handover_server.ps1`.

### BUG-19. У ожидания, повтора и опроса есть конец
**Правило.** У каждого ожидания, повтора и опроса есть конец:

### BUG-20. Клиенту не доверяем
**Правило.** Каждый запрос игрока проверяет решающий (принцип P8): кто, что, где, сколько, как часто, разумны ли числа. Решающий сам

Новая проверка одну Dev-сборку только пишет в журнал «отказала бы», затем включается отказ. Подменять личность игрока ради

если проверка упала.

**Хорошо:** `coop_trust.script:81` `function guard(name, ok, fmt, ...)`; `coop_mods_pdata_pda.script:26`
`return coop_trust.guard("pda_id", ok, "invalid object id in personal PDA state") and id or nil`.

**Проверка:** `будет: S30` (`local function trust(`, `pcall(t.pass` — отказ; `pass(` с безусловным `return` следом —
предупреждение); `test:` запрос изменённого клиента под `log` и `refuse`; ревью: все строки `[coop-trust]` объяснены до
включения отказа.

### BUG-21. Журнал говорит правду
**Правило.** Строка журнала говорит, что на самом деле случилось: отброшено, пропущено или отложено. Она называет объект —
номер, секцию, имя NPC, значения обеих сторон (поколения, метки, цены), — чтобы следующий разбор не требовал новой сборки.
Строка ограничена бюджетом (CPP-8). Диагностика стоит до каждого раннего выхода, который должна видеть. Вылет пишет причину
(код, расшифровку), а не только место, где его заметили. В тексте строки нет кодов работ (`W11:`, `B8:`): журнал читают
люди и проверки стенда.

Порог диагностики («ждёт дольше N») меряют в кадрах или игровом времени и не считают известные заминки загрузки (вход в
уровень, загрузка моделей). Порог по настенным часам засчитывает копиям остановку всего процесса. Объект, который проверяется
не каждый кадр, судят по числу его проверок, а не по прошедшим миллисекундам.

**Почему.** Строка, которая врёт или молчит о главном, превращает разбор в новую сборку с новой диагностикой.

**Плохо:** `talk refused: gone` без номера NPC; строка `[coop-anim] … plays no base motion` стояла после раннего выхода
`drive_mirror` и Т-позу не видела (ТЗ §6.30); `[coop-hands] npc … held … waiting` с порогом 600 мс по настенным часам
засчитывал копиям заминки загрузки 0,8–7 с (ТЗ §6.32, пункт 3); `coop_npc_meet.script:771,773` — коды `W11:` и `B8:` в
тексте строк.

**Хорошо:** `xrCore/gpu_device_lost.h` + `xrDebug::set_device_lost_note` — в FATAL попадают причина `GetDeviceRemovedReason` и
занятость видеопамяти.

**Проверка:** ревью: «что прочитает разбор из этой строки без новой сборки?»; `test:` диагностическая строка срабатывает в
тесте того случая, ради которого её добавили.

### BUG-22. Новые виды строк в журналах стенда — регрессия
**Правило.** После каждого прогона стенда строки «!» и `SCRIPT ERROR` группируются по виду (текст без чисел и номеров) и
сравниваются с прогоном того же сценария на прошлой сборке. Новый вид или выросшее число строк — это регрессия, её
объясняют до выпуска. Строки «!», которые даёт честная игра, чинят или понижают, а не оставляют «известным шумом».

**Почему.** Регрессия, которая не роняет игру, видна только как новый вид строки, а в шуме из сотен «!» её не заметить.

**Плохо:** `Parent of object N from map server 1 refused: no such object` — 68 и 88 строк в прогонах Dev 65 и 0 в прошлых
сборках; нашли только ручным сравнением (ТЗ §6.32).

**Хорошо:** `tools/stand/base_group.ps1:184` `Show-StandLogLines … 'SCRIPT ERROR|attempt to |! \[SCRIPT|…'` показывает строки,
а сравнение со сборкой раньше будет (пакет P2).

**Проверка:** будет: инструмент сравнения видов строк в `tools/stand`, вывод в SC и SS (пакет P2); выпуск — необъяснённых
новых видов нет.

### BUG-23. Действие над игроком — только по его выбору
**Правило.** Действие, которое меняет положение или состояние игрока (телепорт, начало боя, перенос в другое место, забрать
его вещи, сменить ему карту), выполняется только по явному выбору этого игрока: его кнопка, его ответ «да». Не по близости к
месту, не по голосу другого игрока, не по таймеру «все рядом — значит согласны». Ответ «нет» или отсутствие ответа
оставляет игрока на месте. Групповое действие перечисляет тех, кто согласился, и берёт только их.

**Почему.** Арена Бара стартовала сама, когда все игроки стояли в 12 м от Арни, а «да» одного уводило всех рядом; «нет» всё
равно телепортировало (ТЗ §6.19, Р88).

**Плохо:** до правки Р88 — автостарт сбора арены по близости и перенос всех стоящих рядом по одному «да».

**Хорошо:** образец: `participants = { [peer] = true }` наполняется только ответом «да» самого игрока; перенос идёт по этому
списку.

**Проверка:** `test:` «игрок ответил нет / не ответил — его положение не изменилось»; ревью: «кто выбрал это действие для
каждого затронутого игрока?».

### BUG-24. Производное значение обновляет каждый писатель входа
**Правило.** Производное значение (дайджест, хэш, счётчик, кэш) пересчитывается в той же функции, которая меняет его вход,
у каждого писателя этого входа. Не по таймеру и не в одном из путей записи. Список писателей и место пересчёта пишутся
комментарием у значения.

**Почему.** Хэш, который отстаёт от своего списка, даёт вечную пересверку: при каждом входе игрока хост и клиент видят
разные хэши отношений и гоняют StoryResync по кругу (ТЗ §6.32, Р104).

**Плохо:** хэш отношений хоста отстаёт от списка отношений — петля StoryResync при каждом входе (ТЗ §6.32, новая находка).

**Хорошо:** образец: функция, которая меняет запись отношений, сама обновляет хэш отношений (или помечает его к пересчёту в
этом же кадре); сверка только читает хэш.

**Проверка:** `test:` «изменить вход каждым писателем — производное совпало с пересчётом с нуля»; ревью: «кто ещё пишет
этот вход?».

### BUG-25. Игрока ставят туда, где он помещается
**Правило.** Точка появления или перехода игрока — проходимая вершина ИИ-сетки. Игроки, которые появились в одном месте или
стоят у выхода с уровня, не сталкиваются друг с другом, пока не разойдутся на заданное расстояние. Каждая машина решает это
одинаково, по данным, общим для всех машин (BUG-3).

**Почему.** Игроков ставило друг в друга, а столкновение выталкивало только своего актёра — сквозь стену или под карту (ТЗ
§6.10, Р50).

**Хорошо:** `xrCoop/coop_player_touch_rules.h` — пара игроков не сталкивается у выходов и мест появления, пока не разойдётся;
места прибытия берутся из all.spawn (`near_spawn`).

**Проверка:** `test:` нативный тест правила касания; стенд перехода группы в узком проходе.

### DOC-1. Комментарий — это действующее правило
**Правило.** Комментарий объясняет текущее правило и почему оно такое, в настоящем времени. Комментарий верен; если код
меняется, комментарий правится в том же изменении. В комментарии нет истории:
- дат, номеров сборок (b62, Dev 57), раундов и ревью;
- кодов ТЗ / Р / R / W / F / G / P;
- «было», «раньше», «moved»;
- ников тестеров;
- путей в `temp/` и абсолютных путей машины.

Всё это — в git и vault; договор, на который ссылаются, лежит в `docs/contracts/`.

Язык комментариев — английский: C++, Lua, конфиги, инструменты, тесты. Единственное исключение — метка слоя первой строкой
Lua-файла (LUA-7), ровно в своей форме. Коды и номера в комментариях лучше не писать вовсе; если без них нельзя (ссылка на
договор), они пишутся латиницей («R32», а не «Р32»). Шапка файла говорит, что файл делает, а не код работы. Метка нашей правки
в стоке — одна на блок (`// coop:`), после неё правило; пустые метки на каждой строке не ставятся. Правило действует для C++,
Lua, конфигов, инструментов, тестов, наших правок 3rd party и README папок.

**Почему.** История в комментариях устаревает и врёт: ~630 меток и ~185 дат только в `xrCoop`, а «Р32» кириллицей не
находится поиском «R32».

**Плохо:**

- `xrCore/gpu_device_lost.h:1` «RayLink (crash triage, 2026-11-25, report RL-5TE8-EFGE)»;

**Хорошо:** `xrCoop/coop_guarded_call.h:2-4` «The renderer's texture loads are such a call: they run in a task group nobody

## 12. Как добавлять правило

1. Нашёлся новый класс ошибки (ревью, баг игрока, стенд). Сначала проверь, не закрывает ли его уже правило этого файла. Если
   закрывает — добавь пример в «плохо», нового правила не нужно.
2. Если не закрывает — заведи правило в своём разделе со следующим свободным номером. Номера не переиспользуются, удалённое
   правило помечается «снято» с причиной. Заполни все поля: правило, почему, плохо (наш код), хорошо, проверка. Имена,
   файлы и функции в правиле должны существовать; если чего-то ещё нет, пометь «будет: пакет Pn». Пакета нет — так и напиши
   «пакет не назначен» и скажи ведущей.
3. Запиши источник в таблицу покрытия «находка → правило». Сейчас это рабочий файл ведущей вне репозитория; перенос в
   `docs/` будет. Находка, которую правило не закрывает, записывается в §13 с причиной.
4. Если нарушение можно поймать машиной, добавь проверку по TOOL-9: правило в `tools/check_layers.py` (L) или в
   `tools/check_static.py` (S) со следующим свободным номером из §14, набор «поймать / пропустить» в `tests/tools`,
   сегодняшние нарушения — в allow-list с потолком. Один номер — одна проверка. Если нельзя — добавь строку в чек-лист и в
   ревью.
5. Если правило важное, добавь одну строку в «Как писать код» в `CLAUDE.md` и в «How to write code» в `AGENTS.md`.
6. Если правило меняет решение владельца, сначала нужно его слово: строка в ТЗ §2 (OWN-1).

## 13. Что правилом не закрыто

Эти пункты не закрываются правилом о том, как писать код. Каждая строка таблицы покрытия без правила стоит здесь.
