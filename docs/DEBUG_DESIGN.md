## 0. Коротко

- **Сейчас** отладки в коопе по сути нет. Клиентам F7 выключен (R-6.6). У хоста с ключом `-dbg` стоковое F7 работает, но исполняет
  действия прямо в Lua сервера. Получается «игрок-хост = сервер»: ровно то смешение, от которого владелец уходит. Лаунчер `-dbg` не передаёт.
- **Предлагается** одна серверная отладка (как `sv_cheats`):
  - Состояние держит СМ. Включает его ключ `-dbg` или команда `coop_debug on` в консоли сервера.
  - Кнопка в F7 у игрока-хоста — это та же консоль его процесса, а не особый путь игрока.
  - Состояние уходит всем новым сообщением `DebugState`, игроку-хосту по внутреннему каналу. Это **протокол 29**.
- **Запросы клиента** идут готовым механизмом `coop.sync.request` → обработчик в Lua СМ. Игрок-хост уже ходит этим путём по внутреннему
  каналу как узел 0, поэтому путь у всех игроков один.
  - Новые сообщения для запросов не нужны.
  - Движок режет запросы `coop.dbg.*`, пока отладка выключена: только просмотр проходит.
- **Где исполняется:**
  - мировое (время, погода, выброс, инфопорции) — на СМ;
  - личное и спавн — у авторитета карты, на которой стоит игрок: СМ для своей карты и офлайна, Mk для своей; СМ пересылает готовым
    механизмом `add_level_handler`;
  - точку спавна по-прежнему выбирает клиент стоковой формулой, сервер её проверяет.
- **Личные флаги** (бессмертие, бесконечные патроны, невидимость для ИИ):
  - решает сервер, каждая машина ставит флаг своему актёру из `DebugState`;
  - бессмертие дополнительно держит серверный арбитраж попаданий (`stalker_hit`).
- **Выделенный сервер:** `coop_debug on|off` и `coop_dbg <команда> @игрок ключ=значение` в его окне, тот же реестр команд.
- **v1** закрывает около 60 стоковых действий. Редакторы, которые пишут файлы, произвольный Lua от игроков и массовые разрушительные
  команды — вне v1 (§C.3).

### A.4 Выделенный хост и серверы карт

- **Выделенный** (`-coop_dedicated`): роли `WorldServer|MapAuthority` без `Player` (`coop_roles.h:37-42`), актёр — призрак на `fake_start`
  (`coop_dedicated.cpp:403-431`). Внутреннего канала нет (`attach_local(nullptr)`, `docs/DEDICATED_AUDIT.md`). Значит запросов от узла 0
  не бывает: только консоль. Окно консоли — настоящий `AllocConsole`, строки идут в `Console->Execute` (`coop_dedicated.cpp:125-136`).
- **Mk:** авторитет своей карты и клиент мира. Мост с id `0x100+k`, в `peers()` его нет. Игроки его карты — виртуальные узлы. Своих
  обработчиков `coop.sync` у Mk быть не может (A.2 п. 12). Просьбы игроков с его карты доходят событием от СМ с `_peer`.
- **Последствие для отладки:** решение «можно или нельзя» принимает только СМ. Исполнение — у авторитета нужной карты. Mk исполняет
  только то, что переслал СМ.

### A.6 Риски, которые проект должен закрыть

1. Двойной смысл узла 0 (A.2 п. 1–3). В отладке не опираться на `from == 0` как на «право хоста».
2. Стоковые действия меняют мир прямо из UI (A.2 п. 6). В сессии ни одно стоковое действие F7 не должно исполняться локально, у хоста тоже.
3. Произвольный Lua от удалённого игрока на СМ — это выполнение кода на ПК хоста: в Anomaly доступны `io` и `os`. Только оператор.
4. Клиентские читы движка (A.2 п. 11) делают серверную отладку бессмысленной. Их надо гасить в сессии.
5. Разрушительные массовые действия без подтверждения (все отряды, все инфопорции, тысячи аптечек в `game_graph show`).
6. Разделённые карты: СМ не знает графа карты Mk (`level.vertex_id` работает только для загруженной карты). Проверять точку может только
   авторитет карты.
7. Редакторы пишут `configs/**.ltx`. В сессии следующий вход упрётся в сверку файлов (`ContentMismatch`).

## B. Целевая архитектура

### B.1 Принципы

1. **Отладка сервера и отладка клиента — разные вещи.**
   - Серверная — разрешение на изменение мира для всех игроков сессии, хранит СМ.
   - Клиентская — ключ `-dbg` своей машины: только локальные инструменты (оверлеи, свои консольные переменные рендера, лог). Мир она не
     трогает никогда.
2. **Игрок один для всех.** Игрок-хост и удалённый клиент отличаются только каналом (`LocalLink` или сеть). У обоих F7 одинаковый, их
   запросы идут одним путём (`coop.sync.request`), сервер различает их только номером узла.
3. **Право включать отладку — у консоли сервера**, а не у «игрока 0».
   - Консоль есть в процессе СМ: у слушающего хоста это окно игры, у выделенного — окно консоли.
   - Переключатель в F7 у игрока-хоста — просто кнопка этой консоли. Показывается там, где процесс держит роль `WorldServer`
     (`coop.debug.is_operator()`).
4. **Каждое действие клиента исполняет сервер.**
   - Клиент собирает аргументы так же, как сток: цель под прицелом, точку по лучу камеры.
   - Решает и исполняет СМ или авторитет карты.
   - Результат доходит до всех обычной синхронизацией: `EntitySpawn`, `TimeSync`, `WeatherSync`, `InfoPortion`, `MoneyBalance`.
5. **Одиночка не меняется:** вне сессии стоковое F7 и `DEV_DEBUG` работают как сейчас.

### B.2 Состояние отладки на сервере

**Модуль.** Новый `E/xrGame/coop/coop_debug.{h,cpp}`, пространство `coop::debug`. Чистые правила и формат сообщения —
`E/xrCoop/coop_debug_rules.h` (header-only, юнит-тесты).

| Поле | Значение |
|---|---|
| `on` | включена ли серверная отладка |
| `source` | `Off`, `LaunchKey` (`-dbg`), `Console` (`coop_debug on`) |
| `serial` | растёт на каждое изменение, получатель отбрасывает старое |
| `flags[peer]` | личные флаги игрока: бит 1 бессмертие, 2 бесконечные патроны, 4 невидимость для ИИ |

**Кто ставит:**
- **Ключ `-dbg`** (движковый `Core.isDebug()`, точный ключ, не подстрока): процесс, ставший СМ (`Manager::start_host`, выделенный при
  старте сессии), начинает с `on = true`, `source = LaunchKey`.
- **Консоль СМ:** `coop_debug on | off`, без аргумента — состояние. Работает без ключа `-dbg`. `off` выключает и при `-dbg`.
- Выключение снимает все личные флаги.
- **Где команда работает.** В процессе клиента и на Mk `coop_debug on/off` отвечает «отладку включает консоль сервера», показ состояния
  работает везде.

**Сохранение.** Состояние живёт в процессе СМ.
- В сейв мира не пишется.
- Переживает смену мира в той же сессии (`coop_restore`, переход хоста).
- После перезапуска сервера отладка выключена, если нет `-dbg`.
- Флаги игрока снимаются при его уходе (`on_peer_left`).
- Метка сейва «читы использовались» — открытый вопрос F.1.

**Рассылка.** `DebugState` (B.3) уходит:
- всем узлам, игроку-хосту по `LocalLink`;
- каждому мосту Mk;
- при каждом изменении, после `JoinComplete` каждого игрока (и при перезаходе), после `Ready` моста Mk.

**Lua-событие.** На каждой машине при новом состоянии — колбэк `coop_debug_changed(on, source)`, по образцу `coop_world_back`
(`coop_main.script:1197`).

### B.3 Сообщение `DebugState` (протокол 29)

```
DebugState = 0x01A1   (раздел "scripting and diagnostics", свободный код), MsgSender::HostOnly, Lane::Reliable
  u8   on            0 | 1
  u8   source        0 off, 1 ключ -dbg, 2 консоль сервера
  u32  serial
  varu n             n <= kMaxPlayers
  n x { u32 peer, u8 flags }     flags & ~7 == 0, иначе Malformed
```

- Получатель ищет свою строку по `mgr().self()`. Mk берёт всю таблицу: он решает попадания игроков своей карты.
- В той же правке:
  - `kProtocolVersion` 28 → 29 со строкой истории (`coop_protocol.h:15-83`);
  - `msg_name`, `msg_sender` (`coop_protocol.cpp:165`);
  - строка в `kLinkMessages` (`coop_local_link.h:66-79`), иначе игрок-хост сообщение не получит;
  - обработчик в `install_client` модуля, чтобы его увидел сканер `tests/test_handler_tables.cpp`.
- **Почему отдельное сообщение, а не ключ `coop.sync` в области `session`:**
  - флаги нужны C++ клиента (`psActorFlags`) и C++ Mk (`stalker_hit`) без Lua;
  - мосты Mk не входят в `peers()`, и рассылка `coop.sync` до них, по чтению кода, не доходит;
  - отдельное сообщение ровно выражает «игрок-хост — такой же клиент»: он получает его по каналу, как все.
- Любая правка движка всё равно требует нового exe у всех (`BuildMismatch`), поэтому повышение протокола лишних хлопот не добавляет.

### B.4 Единый «игрок» для отладки

Новая функция в общем помощнике `coop_npc_players.script` (там уже `P.object_of_peer` и `with_identity`):

```
P.player(peer) -> nil | {
  peer      = номер узла,
  nick      = ник,
  character = id персонажа в нумерации этой машины (у СМ: 0 для игрока-хоста, прокси для клиента),
  level     = id карты (coop.levels.level_of_player),
  here      = процесс ведёт его карту (у СМ: led_by_host_process; на Mk: игрок его карты),
  link      = "local" | "net",   только для лога и показа
  object()  = game_object персонажа, если он онлайн в этом процессе,
  standing  = на ногах (coop.life_of)
}
P.player_by_name("@Bob" | "@2") -> то же; ник без учёта регистра, #номер
```

- На выделенном `player(0)` — `nil`: призрака в игроках нет (тот же тест исправит A.2 п. 9).
- Никакая команда отладки не ветвится по `peer == 0`. Различие «свой процесс или чужой» есть только внутри `object()` и `here`.

### B.5 Запросы клиент → сервер

**Транспорт.** `coop.sync.request(name, args, cb)`. Пять обработчиков на СМ, лимит у каждого свой (`coop.sync.limit`):

| Имя | Класс | Пока отладка выключена | Лимит (подряд / в секунду) |
|---|---|---|---|
| `coop.dbg.view` | просмотр: сведения сервера, только чтение | проходит | 30 / 10 |
| `coop.dbg.world` | глобальное: время, погода, выброс, инфопорции, респаун | отказ | 5 / 0,5 |
| `coop.dbg.self` | личное: деньги, предметы себе, телепорт себя, флаги | отказ | 10 / 2 |
| `coop.dbg.spawn` | спавн в мир: предмет, NPC, отряд, машина, аномалия | отказ | 10 / 2 |
| `coop.dbg.target` | действие над объектом: убить, удалить, отношения, компаньон, фракция отряда | отказ | 10 / 2 |

Пять имён, а не по имени на команду: у `coop.sync` общий предел 256 обработчиков (`coop_sync_api.cpp:54`), его делят моды.

**Движковый гейт (защита в глубину).** В `on_request` (`coop_sync_api.cpp:1014-1060`) до поиска обработчика:
`debug::refuse_request(name)`. Для `coop.dbg.*`, кроме `coop.dbg.view`, при выключенной отладке ответ «debug is off». Сам Lua-обработчик
проверяет то же. Правило чистое, в `coop_debug_rules.h`.

**Форма запроса** — плоская таблица (вложенные `coop.sync` не берёт):

| Поле | Смысл |
|---|---|
| `v` | версия схемы Lua, сейчас 1. Чужая → `old_client` |
| `cmd` | id команды из реестра (§C), например `spawn_item`, `time_add`, `god` |
| `t` | id объекта-цели в нумерации хоста (`coop.to_host_id` на клиенте) |
| `p` | узел другого игрока (например «телепорт к игроку») |
| `sec`, `n` | секция и количество; `n` ≤ 20, «вся категория» ≤ 100 с `ok = true` после подтверждения в окне |
| `at` | `inv` (в инвентарь) / `point` (по лучу) / `near` (рядом) / `smart` |
| `x`, `y`, `z`, `lv` | точка и вершина уровня, посчитанные клиентом стоковой формулой (A.5) |
| `sm` | имя смарта |
| `a`, `d`, `h`, `m`, `w`, `on` | сумма, дни/часы/минуты, погода, булево |

**Проверки на сервере, по порядку:**
1. Движковый гейт и «в мире» (движок).
2. `v` и `cmd` известны, класс команды совпадает с именем обработчика.
3. `P.player(from)` есть.
4. Схема аргументов: типы, диапазоны, длина строк ≤ 64, секция есть в `ini_sys`, её класс есть в таблице классов спавнера.
5. Цель: объект существует. Не персонаж игрока, не призрак, не id 0 — кроме команд, которые прямо про игрока.
6. Маршрут к авторитету (B.6).
7. Проверки авторитета для точки:
   - `lv` — настоящая вершина его карты;
   - точка в 2 м от `level.vertex_position(lv)`;
   - до персонажа просящего ≤ 200 м;
   - карта точки = карта просящего;
   - gvid берётся с персонажа, данным клиента не доверяем.
8. Исполнение, строка в лог СМ, строка всем игрокам.

**Ответ.** `cb(ok, result)`:
- успех: `{msg = "…", id = …}`;
- отказ: код строкой — `debug_off`, `old_client`, `unknown_cmd`, `bad_args`, `no_player`, `not_standing`, `bad_target`, `player_target`,
  `too_far`, `bad_vertex`, `other_level`, `cap`, `failed`;
- движок сам отвечает `rate limited`, `busy`, `not in the world`, `timeout`;
- `forwarded` — ушло на Mk, итог придёт строкой `coop.dbg.note`.

F7 показывает ответ в своей строке вывода. Отказ переводится через `st_coop_dbg_err_<код>`.

**Объявление.** Каждое успешное изменение мира, спавн, действие над объектом и личный чит дают всем игрокам строку в чат-ленте
(`coop_core_chat`): «[отладка] Bob: AK-74 ×1 себе», «[отладка] Alice: время +6 ч». Как `sv_cheats`: все видят, кто что сделал.

### B.6 Где исполняется команда

| Класс | Где | Как туда попадает |
|---|---|---|
| world | СМ | обработчик `coop.dbg.world` сам |
| self: деньги | СМ (книга денег) | `coop.money_grant(peer, a)` |
| self: флаги | СМ | `coop.debug.set_flags(peer, …)` → `DebugState` |
| self: предметы себе | авторитет карты игрока | СМ: если `here`, сам. Иначе событие `coop.dbg.run` на мост (`coop.levels.bridge_of_player`) с `_peer`, `_rid`, как `add_level_handler` (`coop_main.script:196-217`) |
| self: телепорт | машина игрока по приказу | на своей карте — `coop_mods_core.teleport(peer, pos)`. Другая карта — приказ клиенту выполнить стоковый `ChangeLevel`; движок превращает его в просьбу перехода (`coop_events.cpp:505-509`) с отказами по правилам «сюжетные карты вместе» |
| spawn в точку или рядом | авторитет карты просящего | как «предметы себе» |
| spawn у смарта на карте без игроков | СМ, офлайн | Mk возьмёт объект онлайн обычной передачей, когда рядом окажется игрок |
| target | авторитет карты объекта | СМ: свой объект — сам. Объект Mk — `coop.dbg.run` на его мост; удаление и убийство объекта Mk — готовым приказом `quests.far_do` (`docs/SPLIT_LEVELS.md` §7a «Приказы на Mk») |

- **Mk.** Событие `coop.dbg.run` берётся только от СМ (на Mk `from == 0` — это мост). Mk исполняет ту же запись реестра. `P.player(_peer)`
  на Mk — игрок его карты. Итог он шлёт СМ событием `coop.dbg.done {rid, ok, msg}`, СМ передаёт игроку `coop.dbg.note`. Своих прав Mk не
  проверяет: проверил СМ.
- **Стоковый код «от имени игрока».** Где сток зовёт `db.actor` («отряд — компаньоны актора», «отношение к актору», «предметы актору»),
  авторитет исполняет его внутри `P.with_identity(player:object(), f)`: так уже работают задания и спутники.

### B.7 Консоль сервера

| Команда | Где | Что делает |
|---|---|---|
| `coop_debug [on\|off]` | процесс с ролью `WorldServer` | включает или выключает отладку; без аргумента — состояние, источник, флаги игроков |
| `coop_dbg <команда> [@игрок] [ключ=значение …]` | то же | любая команда реестра §C от имени консоли |
| `coop_dbg help [команда]` | то же | список команд и ключей |

Устройство `coop_dbg`:
- C++-команда зовёт `coop_debug_server.console(line)` через `call_module`, как `parity_command` (`coop_script.cpp:1970-1982`).
- Разбор строки — чистая функция в `coop_debug_rules.h`, с тестами.
- Ответ пишется в лог и в окно выделенного: новая `coop.debug.say(line)` → `coop_console::print`, как `say` в
  `coop_dedicated.cpp:51-56`.
- `@игрок` обязателен для личных команд и спавна «рядом» и «в инвентарь».
- Точку консоль задаёт так: `at=near @игрок`, `at=smart sm=<имя>` или явными `x= y= z=` вместе с `@игрок` (карта игрока).
- Консоль подчиняется тому же `on`, как `sv_cheats`: сначала `coop_debug on`. Существующие админ-команды (`coop_time`, `coop_kick`,
  `coop_restore`) остаются без отладки.
- Произвольный Lua — только здесь: `coop_dbg lua <код>` (оператор) и стоковый `run_string` при `-dbg` на процессе СМ. От игроков никогда.

Примеры:
```
coop_debug on
coop_dbg spawn_item @Bob sec=wpn_ak74 at=inv
coop_dbg spawn_item @2 sec=medkit n=5 at=near
coop_dbg spawn_squad @Bob sec=simulation_bandit_3 at=near
coop_dbg spawn_squad sec=simulation_monolith_5 at=smart sm=pri_monolith
coop_dbg time_to h=6
coop_dbg weather w=w_storm1
coop_dbg surge start
coop_dbg money @Bob a=50000
coop_dbg god @Bob on=1
coop_dbg tp_to_player @Bob p=@Alice
coop_debug off
```

### B.8 Клиент: F7 в сессии, одиночка, локальные читы

- **F7 в сессии** (`kCUSTOM17`) открывает окно `coop_debug_ui` у каждого игрока, у игрока-хоста тоже. Домен `view` в `coop_route.ltx`.
  Вне сессии модуль ничего не делает, работает стоковый F7.
- **Стоковые скрипты отладки** в сессии:
  - домен `none` вместо `host`: не работают нигде, у хоста тоже;
  - заглушки `[route_none_functions]` в любой сессии, не только при `client_mode`.
- **`DEV_DEBUG`** в сессии `false` на всех машинах, у хоста тоже (расширение R-6.6). При конце сессии возвращается прежнее значение.
  Стоковые функции под `DEV_DEBUG` действуют локально: быстрое перемещение к любой метке (`game_fast_travel:37`), метки отладки карты,
  `debug_mode_flag_on`.
- **Окно** берёт режим из `coop.debug.state()`: просмотр (§D) или полное (§C). Каждое действие собирает аргументы стоковой формулой и шлёт
  `coop.sync.request`. Локально мир не меняется: тест подменяет `alife_create_item`, `level.change_game_time` и подобные и проверяет, что
  в сессии их не зовут.
- **Локальные читы движка.** Пока идёт сессия, на процессе без `WorldServer` команды `g_god`, `g_unlimitedammo`, `run_string`,
  `run_script`, `jump_to_level`, `ph_gravity`, `g_end_modif` отказывают со строкой «на клиенте отладку включает сервер», даже при `-dbg`.
  - Реализация: обёртка над регистрацией в `console_commands.cpp:2840-2853`, один вызов `coop::debug::refuse_local_cheat(name)`.
  - На процессе СМ `g_god` и `g_unlimitedammo` в сессии подсказывают «F7 или `coop_dbg god`»: путь флагов один.
  - `run_string` и `run_script` остаются оператору.
- **Защита не от модифицированного клиента.** Здоровье и урон от аномалий клиент считает сам. Это защита честной игры от рассинхрона.

## C. Все стоковые действия и что с ними в коопе

**Классы.**
- **В** — просмотр на своей машине (зеркало ALife клиента, ничего не меняет).
- **ВС** — просмотр через сервер (`coop.dbg.view`).
- **Л** — локальное: только своё представление (камера, оверлей, свои консольные переменные рендера). Доступно при клиентском `-dbg` или
  при включённой серверной отладке.
- **Г** — глобальное, исполняет СМ.
- **Л-П** — личное, для просящего.
- **С** — спавн в мир.
- **Ц** — действие над объектом.
- **О** — только оператор (консоль сервера).
- **✗** — вне v1, причина в столбце.

**«Авт.»** — авторитет карты (B.6). Номера строк — из описи стока: `S/ui_debug_launcher.script` без префикса, остальное с именем файла.

### C.2 Краевые случаи

- **Игрок на другой карте.** Всё, что касается точки или объекта, исполняет авторитет карты (B.6). СМ не проверяет вершины чужой карты:
  у него нет её `level.ai`. Мировое (время, выброс, инфопорции) СМ делает сам. Выброс на картах Mk уже убивает по отчёту машины игрока
  об укрытии.
- **Предметы в инвентарь просящего.** Родитель — персонаж просящего в нумерации авторитета, а не id 0. У СМ для игрока-хоста это 0,
  для клиента — прокси. Тест в пакете 2 проверяет, что запрос от узла 3 никогда не кладёт предмет актору хоста.
- **Деньги.** Только книга СМ (`money_grant`). У игрока-хоста баланс — актёр мира; у клиента `MoneyBalance` придёт с примечанием.
- **Телепорт удалённого игрока.** Сервер приказывает машине игрока, а не двигает прокси: позицию ведёт владелец (`PlayerState`).
  На другую карту — стоковый `ChangeLevel` на машине игрока превращается в просьбу перехода, СМ может отказать («сюжетные карты вместе»,
  занятость). Игрок-хост — по тому же приказу через канал: прямой путь `coop_mods_core.teleport` для `self_peer` убрать (A.2 п. 3).
- **Бессмертие.** Два слоя (B.9). Только локальный флаг не спасёт от `PlayerHit`, только серверный — от аномалий.
- **Время.** Только вперёд (сток не умеет назад, `coop_dedicated.cpp:232`). Множитель меняет СМ, клиенты свой отказывают
  (`coop_worldstate.h:33-37`).
- **Погода.** Ставится на СМ, `WeatherSync` разносит её. Как она ложится на карты Mk со своим циклом (`weather_set`, протокол 11) —
  проверить вживую.
- **Инфопорции и задания.** Только СМ (`InfoPortion`, задания — копия хоста). Выдать задание: в v1 через Lua оператора, команды в F7 нет.
- **ИИ-команды** (логика, компаньон, отношения, отряд к смарту) — у авторитета объекта, «актор» = просящий через `with_identity`.
- **Игрок упал или зритель** (`coop.life_of` ≠ alive): личные спавн и телепорт отказывают с `not_standing`. Мировые команды работают.
- **Загрузка и переход.** Пока игрок не в мире, движок отвечает `not in the world`. При переходе хоста запросы ждут в окне мягкого
  перехода, как весь Lua RPC (`SPLIT_LEVELS.md` §7a).

## D. Режим «только просмотр» (серверная отладка выключена)

F7 у любого игрока, у игрока-хоста тоже, открывает то же окно. Ничего, что меняет мир или персонажа, в нём нет.

| Панель | Что видно | Откуда |
|---|---|---|
| Состояние отладки | «Отладка сервера: выключена». У оператора — переключатель, у остальных подпись «включает хост или консоль сервера» | `coop.debug.state()`, `is_operator()` |
| Цель | Имя, id (свой и хоста), секция, класс, story id, фракция, ранг, репутация, отношение ко мне, отряд и смарт, «видит ли меня» | Своё зеркало (T1, T10); «видит ли» и поля ИИ — `coop.dbg.view` |
| Предметы цели | Инвентарь NPC или ящика | Зеркало (T10) |
| Моё место | Координаты, lvid, gvid, карта, направление; «записать в файл» (A7) | Своя машина |
| Ближайший объект | Имя, секция, id, дистанция до камеры | Зеркало (A11) |
| Игроки | Ник, узел, карта, на ногах или нет, RTT, потери | `coop.players()`, `coop.life_of` |
| Мир | Время и множитель, погода, фаза выброса или пси-шторма | Синхронизированное состояние своей машины |
| Справка | Список команд, которые станут доступны при включённой отладке | Реестр |

Дополнительно при **клиентском** `-dbg` (B.1): локальные инструменты класса Л — `rs_stats`, консольные переменные освещения,
редактор HUD без записи, перечитать ini, свободная камера. Без `-dbg` и без серверной отладки этих инструментов нет.

## F. Вопросы владельцу

1. **Ачивки.** Сток при `-dbg` навсегда помечает сейв `debug_mode_flag_on`, ачивки в нём выключаются (`S/game_statistics.script:248`).
   Помечать мир при включении серверной отладки? Предлагаю как в стоке: да.
2. **Разрушительное — всем или только хосту?** При включённой отладке всем доступно всё из v1 (удалить объект, удалить обычные отряды,
   дать или снять инфопорцию — с подтверждением). Lua — только хосту, это решено (выполнение кода на его ПК). Нужен ли ещё уровень
   «только хост» для удаления объектов и инфопорций?
3. **Консоль сервера тоже ждёт `coop_debug on`?** Предлагаю да, как `sv_cheats`. Уже существующие `coop_time`, `coop_kick`,
   `coop_restore` работают без неё.
