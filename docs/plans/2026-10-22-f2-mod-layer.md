# Ф2. Слой модов — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Цель:** закрыть дыры доверия, которые остались после Ф0, и сделать так, чтобы моды работали в коопе без патчей:
- деньги, создание предметов клиентом и апгрейды решает хост;
- маршрутизатор колбэков и маршрутизатор вызовов работают в движке;
- работают зеркало `m_data` и `coop.sync`;
- синхронизация, которую сейчас ведут Lua-скрипты, переезжает в движок.

**Архитектура:**
- Каждое решение — чистая функция в `engine/src/xrCoop` без зависимостей от движка, с юнит-тестами. Таблицы маршрутов
  и классов вызовов, денежный журнал, хранилище `coop.sync`, разница зеркала устроены так же.
- Код в `engine/src/xrGame/coop` склеивает эти функции с движком и сетью. Он же даёт экспорт в Lua.
- В Lua остаются тонкие прокладки:
  - `coop_route.script` — над стоковым диспетчером колбэков;
  - `coop_mirror.script` — снятие и применение `m_data` через `marshal`;
  - `coop_sync.script` — сохранение областей `coop.sync` в сейв хоста.
- Lua-протоколы поверх `coop.send_event` переходят на `coop.sync` и на сообщения движка.

**Стек:** C++17 (MSVC 2022, xray-monolith `ad9d841660`, `engine/src/xrCoop`, `engine/src/xrGame/coop`), Lua 5.1 /
LuaJIT 2.0.4 движка, `marshal` (lmarshal), ENet, Python 3.14 для проверочных скриптов в `tools/`.

**Спецификация:**
- `docs/MOD_LAYER.md` — целиком;
- `SYNC_SPEC.md` §6, §7, §8, §10;
- `TZ.md` — строка Ф2 и принципы P1–P8;
- `REVIEW_FINDINGS.md`: R1 «Перенос в движок» и I5, R4 7, R5 I3 и I4, R6 I-1…I-5, (a) и (b).

База: движок `c023f48` (ветка `coop`), проект `041ce30`. Ф1 параллельно меняет только `tools/`, упаковку, тексты и
документы.

## Global Constraints

- **P1, P8.** Хост авторитетен, клиенту не доверяем. Любое число из сети хост проверяет до использования: кто, что, где,
  сколько, как часто, NaN и бесконечность (`xrCoop/coop_validate.h`).
- **P2–P4.** Моды не переписываем. Мод работает, потому что движок по-своему отвечает на вызов или колбэк. Патч мода —
  крайний случай, и строится он на `coop.sync`, а не на своём протоколе.
- **P5.** Наши файлы не перекрывают стоковые и чужие:
  - конфиги — только уникальные имена `coop_*.ltx`, DLTX `mod_*.ltx`, modxml;
  - стоковые Lua-функции оборачиваем во время работы, файлы не заменяем;
  - мод выключен или урезан — запись в `docs/MOD_REPLACEMENTS.md` в том же коммите.
- **P9.** Строки — только `rus` и `eng`. Русский xml — в cp1251.
- Зеркало `m_data`: снимок у хоста не чаще 1 раза в 2 с. Клиент свои изменения `m_data` не рассылает (MOD_LAYER
  §2.4).
- Гарантии `coop.sync` (SYNC_SPEC §6.5):
  - порядок внутри области сохраняется;
  - вошедший игрок догоняет всё объявленное;
  - данные из сети проверяются по типу и размеру до передачи в Lua;
  - ошибка в Lua-обработчике не рвёт сессию;
  - счётчики видны в `coop_status`.
- **Сообщения.** Новые сообщения Ф2 берут номера только из `0x0190–0x019F`. Ф3 берёт `0x01C0–0x01CF`. Перечисление
  `Msg` только дописывается.
- **Версия протокола.** Задача, которая меняет раскладку, дописывает строку в историю `kProtocolVersion`
  (`xrCoop/coop_protocol.h:14-21`) и тест `protocol_version_bumped_for_<task>` в `tests/test_wire.cpp`. Число ставит
  ведущая при коммите, по порядку коммитов. Счётчик общий с Ф3.
- **Стиль.** Строгая типизация, без хаков. Таб, комментарий `// F2 T<n>: …` у правки. Окружающий стиль `coop_*.cpp`.
- **Агенты.** Не больше 4 одновременно. Агенты не коммитят: коммитит ведущая после проверки. Свои файлы — по таблице.
  В брифе перечисляются и файлы, которые трогать **нельзя** (урок Ф0, задачи 6 и 10).
- **Временные файлы** — только в `temp/`.
- **Проверка.**
  - Компиляция: `tools/compile_files.sh <пути от engine/src/xrGame>` → 0 ошибок. Линковку она не проверяет.
  - Полная сборка (ведущая, в конце каждой волны): `python tools/ci_sync.py`, затем MSBuild
    `engine-ci/src/engine-vs2022.sln -p:Configuration=DX11-AVX -p:Platform=x64` → `exit=0`.
  - Юнит-тесты: `tools/build_tests.cmd [фильтр]` → `temp/tests/coop_tests.exe`, код выхода 0.
  - Lua: `tools/test_lua.cmd [фильтр]` → код выхода 0.
- **Игру не запускать.** Живые сценарии — задача 25, по слову владельца.
- **Документы живые.** Поведение меняется — его часть `MOD_LAYER.md` / `SYNC_SPEC.md` правится в том же коммите.

## Review Focus

Пять ситуаций, которые спецификация подразумевает, а тесты задач по отдельности не ловят. Самая вероятная — первая.

1. **Честный клиент получает деньги без хоста.** Примеры: выплата в диалоге, награда мода через `give_money`. Свыше
   допуска хост откажет, и баланс у клиента «прыгнет» назад.
   - Ожидание: отказ виден в `coop_status` с причиной. Баланс у клиента совпадает с хостом через ≤ 1 запрос.
   - Тест: `ledger_gain_refused_then_view_matches_host`, задача 1. Плюс живой сценарий 25.1.
2. **Сейв/загрузка хоста или переподключение, пока изменения денег и `coop.sync` в полёте.**
   - Ожидание: изменения старой эпохи отброшены. После входа клиент видит баланс и области из сейва хоста. Нет ни
     дюпа, ни потери подтверждённого.
   - Тесты: `ledger_client_view_after_reset` (задача 1), `sync_store_full_replaces_after_reset` (задача 13).
3. **Мод регистрирует свой колбэк (`AddScriptCallback`) или подписывается раньше `coop_route`.** У клиента
   запускается мировая логика, которой нет в списках.
   - Ожидание: колбэк получает домен `owner`. Его мировые вызовы уходят хосту запросом или получают отказ, локально
     не исполняются. Ранние подписки переклассифицируются с сохранением порядка.
   - Тест: `route_shim_unknown_script_world_call_is_gated`, задача 10.
4. **Ключ `m_data` со ссылками на одну таблицу, userdata `CTime` (`__persist`) или кешем подтаблицы в моде** (Hideout
   Furniture держит `player_created_stashes`).
   - Ожидание: применение на месте сохраняет таблицы-получатели, `CTime` восстанавливается, циклы не ломают разбор.
   - Тест: `mirror_merge_keeps_identity_and_ctime`, задача 15.
5. **Предмет с данными в области `object:<id>` переходит из рук в руки** (клиент → земля → другой клиент) или
   уничтожается.
   - Ожидание: данные едут с предметом. Писать их может новый владелец, старый — нет. После уничтожения данные удалены
     у всех.
   - Тест: `sync_object_scope_follows_owner`, задача 14.

## Решения плана (приняты ведущей, причины)

| Решение | Причина |
|---|---|
| Баланс игрока — `m_dwMoney` его прокси на хосте. Клиент шлёт изменение с причиной, а не абсолютную сумму | Хранилище и сейв уже есть. Хост проверяет каждое изменение (TZ Ф2, R4 7). Деньги из диалогов и модов клиент получает по допуску, а не сам по себе |
| Апгрейд оплачивается одним запросом: событие апгрейда несёт механика и сумму, хост проверяет и списывает | Устраняет двойное списание (Lua-эффект плюс хост). Механик и цена проверяются в одном месте |
| ReqSpawn: класс неизвестен — отказ (раньше «прочее»), квестовые предметы — отказ, бюджет стоимости на игрока | `clsid` задаёт только движок, моды новых классов не вводят. Бюджет закрывает «сколько» из P8 и не ломает крафт |
| Домен определяется по колбэку. Незнакомый скрипт получает домен колбэка, по умолчанию `owner`. Старые списки по скриптам становятся переопределениями | MOD_LAYER §2.2, R5 I4: у клиента заработают мины, верстак, тихие убийства. Мировые вызовы клиента защищает маршрутизатор вызовов |
| Домены: `host`, `owner`, `view`, `none` (`blocked` — синоним), `level` | `level` зарезервирован под Ф3a и до неё ведёт себя как `host` |
| В C++ API `coop.sync` живёт в `coop::syncapi`, в Lua — `coop.sync` | Пространство `coop::sync` уже занято (`coop_sync.cpp`) |
| Области `world`, `player`, `object` хранятся в сейве хоста как ключ `m_data.coop_sync` | `.scoc` пишет стоковый Lua. Отдельный файл сейва потребовал бы правки движкового сохранения |
| Зеркало не вызывает общий `save_state`. Оно снимает живой `m_data`, а `save_state` вызывает только у скриптов из списка `[mirror_live_save]` | Общий `save_state` раз в 2 с имеет побочные эффекты у модов (чистка, `pstor`) |
| Настройки хоста — область `session` в `coop.sync`, без нового сообщения | Полная копия при входе и изменения уже есть в API |
| Выброс — существующее `Msg::Emission` (0x0162), сейчас неиспользуемое | Без нового номера |
| Задания: запросы клиента — `coop.sync.request` с проверкой хостом в Lua (`run_as`). `TaskReqState` движка проходит ту же проверку | Условия заданий — Lua стока. Закрывает «завершить любое задание» (R4 2, R6 I-1) |
| Сон, ожидание и пропуск времени (`economy.propose/vote/ballot/verdict/skip/fade`) в Ф2 **не переносятся**, их делает Ф3 | Ф3 меняет саму политику — общий сон (`docs/CHECKPOINTS_DEATH.md` §4). Перенос дважды — лишняя работа и конфликт файлов |
| `economy.tp` — запрос в `coop.sync` с проверкой точки, а не `LevelChange`, как предлагало R1 | Это телепорт группы внутри уровня, а не смена уровня |
| Для Lua-тестов реальная таблица маршрутов подключается в `runlua.exe` нативным модулем | MOD_LAYER §5: стаб-тесты на таблице по умолчанию, а не на её копии в заглушке |
| Заглушки Lua-тестов каждой задачи лежат в своём файле `tests/lua/support/stubs.d/*.lua` | Параллельные задачи не правят один `stubs.lua` |
| Колбэки «на игрока» у хоста (подмена `db.actor` для прокси, MOD_LAYER §6) — вне Ф2 | По спецификации это разведка по модам GAMMA в Ф4. В Ф2 `as_player` остаётся в Lua |
