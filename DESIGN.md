# Anomaly Coop — архитектура v0.1

Дата: 2026-10-20. Статус: проект, ни одна строка кода ещё не собрана и не проверена в игре.
База: открытый движок `xray-monolith` MT `ad9d841660` (X-Ray 1.6 → Monolith → modded exes).
Ссылки вида `файл:строка` даны по этой ревизии (`..\xrRazom-RE\src\xray-monolith-mt\src\`).

## 0. Цель и чем мы лучше

Кооп для Anomaly 1.5.3 и GAMMA: один живой мир на хосте, к нему подключаются друзья.

| Критерий | Цель v1 | Как сейчас у других (по открытым описаниям) |
|---|---|---|
| Покупка CoP / Steam | не нужны: свой транспорт | xrRazom: в Steam-режиме CoP нужен у всех |
| Проброс портов / Radmin | не нужен: прямой IP → ICE (STUN) → свой relay | Radmin/Hamachi как костыль |
| Игроков | до 8 (тестируем 2 → 4 → 8) | 5 у xrRazom, 2–4 у AT |
| Дюпы предметов | исключены устройством: владение предметом меняет только хост | дюп патронов на загрузке сейва (жалоба на xrRazom) |
| Персонаж | привязан к ключу игрока, ник — просто подпись | смена ника = новый персонаж |
| Сейвы | пишет только хост, клиентские автосейвы невозможны | «автосейв с клиента не грузить» |
| Несовпадение модов | экран со списком различающихся файлов | строка `cfg-diff` в логе |
| Смерть | ранение → поднять напарником, режим смерти настраивается | только downed или только респавн |
| Переход между локациями | вся группа, по готовности | через хоста / клиент сам не может |
| Код | открытый (наши файлы — MIT, сборка в целом — некоммерческая лицензия GSC) | закрыт |

## 1. Ограничения

- **Clean-room.** Источники — только движок выше, код с совместимой лицензией (OpenXRay под MIT, GNS под BSD-3)
  и общие знания. Файлы xrRazom и Anomaly Together не открываем. Код OMP и STALKER-MP без лицензии,
  OMP x64 под AGPL — оттуда только идеи.
- **Лицензия GSC:** только некоммерчески. Никаких платных сборок, ранних доступов за деньги, Boosty-патчей.
- **Не публикуем файлы игры.** Своё — исходники движковых правок, наши скрипты и конфиги, лаунчер.
- **Не обходим покупку.** Steam AppID 480 и подобное не используем.

## 2. Что уже есть в движке (по разведке исходников)

- **Сингл и так клиент-сервер.** `xrServer` (`IPureServer`) и `CLevel` (`IPureClient`) живут в одном процессе.
  Опция `/single` включает `psNET_direct_connect` (`xrNetServer/NET_Server.cpp:250-251`), и пакеты ходят
  прямыми вызовами: вверх — `Level_network.cpp:300-305`, вниз — `xrServer.cpp:797-806`.
- **Остался весь MP из ЗП, и он компилируется.** `game_sv_mp`/DM/TDM/AH/CTA, `CActorMP`, интерполяция и
  предсказание игрока (`Actor_Network.cpp:303-1317`), догоняющий спавн для зашедшего позже (`xrServer_CL_connect.cpp:9`),
  проверка владения в событиях (`xrServer_process_event_ownership.cpp:64-68`). Он спит: MP-квары не регистрируются
  (`console_commands.cpp:2599`), GameSpy — заглушки.
- **Транспорт — DirectPlay8**, порты 1234–1238, до 32 игроков. Другого транспорта нет.
- **Сообщения:** `NET_Packet` до 16 КБ, `M_*` и `GE_*` в `xrServerEntities/xrMessages.h`; обновления объектов
  идут ненадёжно, спавн и события — надёжно, троттлинг 30 Гц.
- **Что прибито к одиночке:**
  1. `IsGameTypeSingle()` — около 195 мест, `GameID()` — около 115.
  2. `SendUpdatesToAll` в сингле ничего не делает (`xrServer.cpp:349`).
  3. ALife создаётся только в `game_sv_Single` и требует `single` (`alife_simulator.cpp:59-62`); онлайн и оффлайн
     считаются по расстоянию до единственного актора (`alife_dynamic_object.cpp:133-185`).
  4. `Actor()` падает вне сингла (`Actor_Network.cpp:62`), около 369 вызовов; `g_actor` перезаписывает любой
     локальный игрок (`Actor_Network.cpp:532`).
  5. Переход на другую локацию сносит сервер, ALife и Lua целиком (`Level.cpp:956` `MakeReconnect`).
  6. Задания жёстко привязаны к актору с id 0 (`GameTaskManager.cpp:50`); диалоги, ПДА, торговля и HUD
     опираются на `Actor()`.
  7. Скриптовые биндеры обновляются у всех объектов на любой машине — ограничения нет
     (`script_binder.cpp:204`).

## 3. Ключевые решения

**D1. Один мир — на хосте.** ALife, ИИ, квесты, аномалии, время и погода считаются только у хоста.
У клиентов своего ALife нет: они рисуют мир по пакетам хоста. Это убирает целый класс рассинхронов
«два мира, которые пытаются совпасть».

**D2. Свой игрок — у владельца.** Движение, камера, физика, оружие и состояние (здоровье, голод, радиация)
своего персонажа считает его клиент и отправляет хосту; остальные видят его через готовую интерполяцию
из `Actor_Network.cpp`. Поэтому стрельба клиента ощущается как в сингле.

**D3. Транспорт — Valve GameNetworkingSockets** (BSD-3), статически, крипто BCrypt (без OpenSSL).
Основа — разделение `BaseServer/BaseClient` и рецепт сборки из OpenXRay PR #2190 (MIT).
DirectPlay не трогаем и не используем. Клиент самого хоста остаётся внутрипроцессным.
Сеть обслуживается в главном потоке (`ReceiveMessages` в `net_Update`), чтобы обойти гонки
DirectPlay-потоков, о которых говорит разведка.

**D4. Новый тип игры `coop`.** Бит `eGameIDCoop`, `game_sv_Coop : game_sv_Single` (ALife и сюжет остаются),
`game_cl_Coop : game_cl_Single` (интерфейс сингла). Признак `single` разводим на два смысла:
- `IsSingleLikeRules()` — правила сингла: инвентарь, состояние актора, интерфейс, ALife. Истина для single и coop.
- `IsLocalOnlySession()` — сети нет: прямое соединение, без рассылки обновлений. Истина только для single.

Все ~195 мест классифицируем скриптом и правим по таблице, не вслепую.

**D5. Предметы меняют владельца только через хост.** Подобрать, выбросить, обыскать, переложить в тайник,
купить, продать — это запрос к хосту. Он одобряет первый запрос (`GE_OWNERSHIP_TAKE`) и отклоняет
остальные (`GE_OWNERSHIP_REJECT`). Сохранение на хосте атомарно: перед записью он дожидается, пока
закончатся операции, что уже в полёте. Это закрывает оба известных класса дюпов: двое схватили
одновременно и дюп на сейве/загрузке.

**D6. В Lua три домена выполнения.**
- `host` — квестовая логика, `xr_logic` NPC, `alife()`, таймеры мира. Выполняется только у хоста.
- `owner` — биндер своего актора, его эффекты и использование предметов. Выполняется у владельца.
- `view` — интерфейс, HUD, звуки и визуальные эффекты. Выполняется везде.

Домен задаётся манифестом `coop_domains.ltx` по имени скрипта. По умолчанию домен `host`, клиентские
скрипты разрешаются списком. Фильтр стоит в диспетчере колбэков Anomaly и в `CScriptBinder`
(биндер удалённого объекта не обновляется, если не помечен `view`). Так аддоны GAMMA классифицируются
без правки их файлов.

**D7. Вся группа всегда на одной локации.** Движок держит одну локацию на сервер. Переход: игрок у
перехода → проверка готовности группы → хост меняет уровень и переносит всех акторов → клиенты
автоматически переподключаются по токену сессии. Готовое сообщение для образца — `M_CHANGE_LEVEL_GAME`.

**D8. Сейв только у хоста, персонажи — по ключу.** Каждый удалённый игрок — ALife-объект нового класса
`CSE_ALifeCoopPlayer` (производный от `CSE_ALifeCreatureActor`) с инвентарём, деньгами, группировкой,
состоянием и позицией. Ключ игрока — случайные 128 бит в `appdata\coop_player.key`. Хост сопоставляет
ключ с персонажем. Пока игрок не в сети, его персонаж «запаркован» и не уходит в оффлайн-симуляцию.

## 5. Протокол

- **Lanes GNS:** 0 — надёжные упорядоченные (спавн, удаление, события, RPC); 1 — ненадёжные (снимки);
  2 — надёжные с низким приоритетом (догоняющая загрузка, большие пакеты).
- **Своё семейство сообщений** `M_COOP_*` с отдельного диапазона номеров; готовые `M_*`/`GE_*` переиспользуем,
  где семантика совпадает.
- **Рукопожатие:** версия протокола, id сборки движка, версия мода, ключ игрока, ник, манифест модлиста
  (хеш дерева gamedata и списка `db\mods`). При несовпадении хост присылает свой список, клиент показывает разницу.
  Основа — существующая проверка хеша gamedata (`xrServer_CL_connect.cpp:190-257`).
- **Вход:** загрузка той же локации → догоняющий спавн всех онлайн-объектов из зоны интереса →
  спавн своего актора (локально у себя, удалённо у остальных) → `CLIENTREADY`.
- **Зоны интереса:** у каждого клиента свой набор объектов вокруг его актора. Частота: ближе ~50 м — 20 Гц,
  средняя дистанция — 10 Гц, дальняя — 2–5 Гц. Отправляем только то, что изменилось, с квантованием.
- **Бюджет:** до ~100 КБ/с на клиента при плотной перестрелке. Хост на 7 клиентов — до ~6 Мбит/с исходящего.
  Цифры прикидочные, проверяем замером на S5.

## 6. Подсистемы

### 6.1 Транспорт
Новые файлы в `src/xrNetServer/gns/`, по образцу разделения из OpenXRay: `CoopServer`/`CoopClient` поверх
`IPureServer`/`IPureClient`. Внутрипроцессная связь хоста с собой остаётся. Консоль: `coop_host <port>`,
`coop_connect <ip:port>`, `coop_status`.
Для тестов используем встроенную в GNS эмуляцию задержки и потерь (`FakePacketLag`/`FakePacketLoss`).

### 6.2 Тип игры
`eGameIDCoop` в `gametype_chooser.h`, фабрика в `object_factory_register.cpp`, разбор строки
в `GamePersistent.cpp:238-262`. Строка старта: `<save|level>/coop/alife/new|load`.
`psNET_direct_connect` больше не выводится из строки `/single`, а решается для каждого клиента отдельно.

### 6.3 Игроки и `Actor()`
- `Actor()` = «локальный игрок этой машины». Для HUD, камеры, ПДА и окон это и так правильный смысл.
  Утверждение `GameID()==Single` ослабляем до `IsSingleLikeRules()`.
- Серверной логике, которой нужны «игроки вообще», даём `Level().coop_players()`. Сюда относятся
  выбор врага, пси-атаки контролёра (`controller_psy_hit.cpp`), память врагов (`monster_enemy_memory.cpp`),
  выброс, аномалии, переключение ALife.
- `g_actor` назначается только для своего управляемого актора, а не для любого `LOCAL+ASPLAYER`
  (`Actor_Network.cpp:532`).

### 6.4 ALife с несколькими наблюдателями
Объект онлайн, если до **ближайшего** игрока не дальше `online_distance`. Правки в `alife_dynamic_object.cpp:133-185`,
`alife_online_offline_group.cpp:226,263`, `alife_group_abstract.cpp:164`. Персонажи игроков в сети не уходят в оффлайн.

### 6.5 NPC и мутанты у клиентов
У клиента ИИ не работает. Объект ведётся снимками: позиция, поворот, скорость, тип движения, поза тела,
**id выбранных анимаций** (берём с хоста из менеджера анимаций, а не угадываем), предмет в руках и его
состояние, здоровье, взгляд. Выстрелы, крики и реплики NPC приходят событиями. Смерть: хост шлёт импульс,
у клиента рэгдолл косметический, затем финальная поза.

### 6.6 Бой
Свою пулю клиент симулирует сам (`CBulletManager`). Попадание по NPC отправляет заявку (цель, кость, сила, направление,
тип патрона), хост проверяет её на правдоподобие и применяет. Пули NPC считает хост; попадание по чужому
игроку отправляет его владельцу. Трассеры и звуки выстрелов у всех строятся по событиям выстрела.
Гранату после броска ведёт хост.

### 6.7 Инвентарь, лут, торговля, тайники
Всё по D5. Съесть или использовать предмет: владелец просит → хост удаляет объект → владелец применяет эффект.
Разрядить или разделить пачку патронов: новые объекты создаёт хост по запросу. Деньги — у каждого свои.
Тесты на гонки встроены (см. §8).

### 6.8 Lua
Домены D6. Нужны:
- фильтр в диспетчере колбэков (`axr_main`) и в `CScriptBinder::shedule_Update`;
- API `coop.*`: `is_host()`, `is_client()`, `players()`, `player_by_key()`, `send_rpc()`, `on_rpc()`, `party_has(section)`;
- у клиента — зеркало `alife()` только для чтения по онлайн-объектам. Записи в него превращаются в RPC к хосту.

Сейчас у Lua нет приёма пакетов (`level.send` есть, а хука нет) — добавляем.

### 6.9 Диалоги, задания, ПДА
- **Диалог** выполняется на хосте от имени актора того игрока, который начал разговор. Окно у клиента
  получает варианты фраз и отправляет выбор (`UITalkWnd.cpp:57`, `PhraseScript.cpp:46-79` перестают
  опираться на `Actor()`).
- **Задания** общие для группы: хранятся у актора с id 0, список реплицируется всем. Награду получает
  тот, кто сдал задание.
- **Квестовые предметы** проверяются по инвентарю всей группы через `coop.party_has()` с патчами
  ванильных проверок. Так уходим от ограничения «отдай предмет хосту».

### 6.10 Переходы, сейвы, переподключение
- **Переход между локациями.** `change_level` переносит всех игроков, а не одного
  (`alife_update_manager.cpp:160-245`). Клиенты получают `M_COOP_CHANGE_LEVEL {level, token}`, показывают экран
  загрузки и сами переподключаются, когда хост поднял сервер.
- **Обрыв связи.** Персонаж игрока паркуется на месте. Сервер ждёт его N минут, затем отправляет в безопасное место.
- **Загрузка сейва.** Игроки, которых ещё нет в сети, остаются запаркованными до входа.

### 6.11 Мир
- **Время и погода.** Ведёт хост, клиенты получают синхронизацию. `game_cl_Coop` берёт время не из ALife
  (у клиента ALife нет), а из этих пакетов.
- **Выброс и пси-шторм.** Сценарий крутится на хосте. Фазы уходят клиентам событиями, эффекты рисует клиентский скрипт.
  Укрытие и урон хост считает по позиции каждого игрока.

### 6.12 Смерть
При нулевом здоровье игрок не умирает, а падает раненым с таймером кровотечения. Напарник поднимает его
аптечкой. Если таймер истёк, игрок погибает, дальше по настройке сервера:
- хардкор — наблюдает за группой до загрузки;
- респавн на базе с потерей снаряжения;
- респавн с сохранением снаряжения.

Наблюдателя берём из MP (`CSpectator`).

### 6.13 NAT
1. **v1:** прямой IP и IPv6 плюс инструкция для Tailscale/ZeroTier/Radmin.
2. **v2:** ICE в GNS со STUN и маленьким сервером сигналинга (WebSocket) на своём VPS.
3. **v3:** TURN (coturn). Включаем только после своих тестов: у GNS открыт баг #452, relay-only через coturn
   отваливается.

## 7. Риски (по убыванию)

1. **Lua GAMMA.** Сотни аддонов пишут в `db.actor` и `alife()`. Защита: домены с умолчанием `host`, журнал
   ошибок клиентских скриптов, совместимость наращиваем по популярности аддонов.
2. **Анимации NPC у клиента.** Риск — «скользящие» сталкеры. Защита: передаём id анимаций, а не состояния,
   и прогоняем тест на сценке у костра.
3. **Переход между локациями** — полный перезапуск сервера. Защита: делаем рано (S9) и прогоняем на каждом срезе.
4. **Многопоточность MT** (параллельный ALife, антифриз спавна). Защита: сеть только в главном потоке;
   спавны и события, которые приходят по сети, проходят через ту же очередь, что и локальные.
5. **Около 195 проверок single.** Защита: таблица классификации, правка по категориям, сборка на каждом шаге.
6. **Трафик.** Защита: зоны интереса, частоты по дистанции, замеры с первого среза, где двигаются NPC.
7. **Два экземпляра игры на одном ПК** нужны для отладки. Не проверено — проверяем на S0.

## 8. Как проверяем

- **Оракул — живая игра.** Хост и клиент на одном ПК: два экземпляра с разными `fsgame.ltx` и пользовательскими
  папками, связь через `127.0.0.1`. Скриншоты обоих окон рядом, сверка по логам `[coop]`.
- **Тесты без игры.** Отдельный exe с юнит-тестами нашего сетевого слоя: сериализация, рукопожатие,
  арбитраж владения (гонка «двое берут один предмет» → ровно один получает), интерполяция.
- **Плохая сеть.** Эмуляция GNS: 100 мс, 200 мс, 2% и 5% потерь.
- **Запись и повтор пакетов.** Готовый механизм `Level_network_Demo.cpp` для разбора рассинхронов.
- **Тестовые команды в консоли.** `coop_test_pickup_race`, `coop_dump_state` — снимок состояния объекта с обеих сторон.

## 9. Не делаем в v1

Игроки на разных локациях одновременно, миграция хоста при его уходе, выделенный сервер, голосовой чат
(есть Discord), транспорт.

## 10. Архитектура v0.2 — «зеркальный мир» (2026-10-20, заменяет D3/D4/§6.2–6.3 v0.1)

Решение владельца 2026-10-20: делать весь кооп сразу по логике из `logic-md/` и SPEC.md. Логика существующего мода
(хост авторитетен, клиент без своего ALife рисует мир по пакетам хоста, чужой игрок — прокси-NPC) берётся как
поведение. Реализация своя, с исправлением его слабых мест (аренда id, сверка «по похожести», отдельный файл игроков).

**Почему не v0.1.** v0.1 вела всех через MP-трубы движка (`game_sv_mp`, ~195 проверок `IsGameTypeSingle`, ~369 вызовов
`Actor()`). Это переписывание половины игры, а интерфейс, ПДА, диалоги и скрипты Anomaly всё равно ждут одного актора.
В v0.2 у каждого игрока обычная одиночная игра со своим `Actor()`. Кооп — слой поверх неё.

| Что | Как в v0.2 |
|---|---|
| Транспорт | ENet (MIT, вендорим в `src/3rd party/enet`), за интерфейсом `coop::Session` (`src/xrCoop/`). Каналы: 0 надёжный, 1 ненадёжный (снимки), 2 надёжный объёмный (сейв мира). Звезда: клиенты говорят только с хостом. |
| Вход в мир | Хост сохраняет мир (`.scop` + Lua-часть Anomaly `.scoc`) и шлёт клиенту блобом. Клиент грузит его → **все id сущностей совпадают** с хостом. Сверка «по похожести» не нужна вообще (P2). |
| Свой персонаж клиента | На хосте — прокси-сталкер секции `coop_player_avatar` (ключ игрока в custom data). Его инвентарь — обычные предметы мира в сейве хоста (P4). После загрузки у клиента роли меняются: актор (id 0) забирает позицию, деньги, группировку, инвентарь прокси, а прокси получает данные актора хоста и становится аватаром хоста. Отображение id: `0 ↔ proxy_k`, остальные id равны (`join::to_local/to_host`). |
| Чужие игроки | Аватары (прокси-сталкеры) без ИИ, ведутся снимками 20 Гц: позиция, повороты, скорость, флаги движения, MotionID ног/торса/головы (визуал тот же → id анимаций те же), активный предмет. Интерполяция с задержкой 100 мс, свой актор без задержки. |
| NPC и мутанты у клиента | ALife клиента заморожен. Онлайн/оффлайн, спавн, удаление, смена владельца приходят от хоста. Объекты на клиенте — удалённые: без ИИ и без логики биндеров, позы и анимации из снимков хоста. |
| Создание/удаление сущностей | Только хост (P7). Клиентский спавн перехватывается и уходит запросом; хост создаёт сущность своим генератором id и рассылает её с этим id, клиент создаёт с тем же id. Аренды диапазонов id нет — класс багов «id занят загруженным миром» исчезает. |
| Предметы | Владение меняет только хост: запросы взять/выбросить/переложить/использовать, хост применяет первый, рассылает итог. |
| Сейв | Только хост (у клиента сейв запрещён). Персонажи игроков — внутри сейва хоста как прокси (P4). |
| Диагностика | `coop_status` (игроки, RTT, трафик по типам), `coop_dump [id]` (снимок онлайна в нумерации хоста), `coop_netsim lag jitter loss`. |

Структура кода: `src/xrCoop/` — сеть без зависимостей от движка (+ юнит-тесты `tests/`); `src/xrGame/coop/` — слой игры
(`coop_manager` сессия и фазы, `coop_join` вход и смена ролей, `coop_world` реестр аватаров, `coop_players` снимки игроков,
`coop_entities` зеркалирование мира, `coop_console` команды). В движке — только тонкие врезки с пометкой `Anomaly Coop`.
